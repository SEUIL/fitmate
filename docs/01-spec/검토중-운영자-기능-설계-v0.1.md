## 1. 결론과 승인 전 가정

운영자 기능은 별도 관리 영역으로 분리하고, **신고 처리와 회원 보호를 중심으로 한 작은 운영 도구**로 만든다. 회원·콘텐츠·신고 화면을 따로 만들되 동일 대상의 처리 이력으로 연결한다. 단순히 상태만 바꾸는 버튼이 아니라 사유·결과 통지·감사 기록까지 하나의 동작으로 설계한다.

사용자가 시안과 구현 진행을 승인하여 **Android 앱 안의 운영자 센터**로 프론트 데모를 구현했다. 플랫폼과 시안 승인은 아래 제재 기간·권한·보유기간·신규 API 계약 전체의 확정을 의미하지 않는다.

### 현재 프론트 구현 상태 (2026-09-14)

- 설정의 개발용 운영자 데모에서 진입하는 현황 / 신고 목록 / 신고 상세 / 제재 입력·확인 화면을 구현했다. 광고 연결은 제거했다.
- 검색·상태 필터, 검토 시작, 반려·경고·기간 정지를 가상 신고에 적용할 수 있다. 실제 회원/서버/DB/알림에는 반영하지 않는다.
- 회원·콘텐츠 탭은 신고와 연결된 가상 목록이며, 독립 회원 관리·콘텐츠 조치 및 더보기 운영 도구는 미구현이다.
- 역할/MFA, 비동기 로딩·오류·409, 영구 정지·해제, 사용자 결과·이의신청은 아직 구현하지 않았다. 아래 API는 여전히 제안이다.
- `testDebugUnitTest`, `assembleDebug` 통과. 신규 단위 테스트 3개 통과. 연결된 Samsung 기기에서 `AdminCenterDeviceTest` 1개 통과(신고 검토→기간 정지 확인→완료, 사유 필수·재처리 차단). 설정부터의 전체 진입·회전·다크모드·실서버 왕복은 이 테스트 범위에 포함되지 않는다.
- 초기 실기기 테스트는 잠금 화면 때문에 실행 실패했으며, 잠금 해제 후 동일 테스트가 통과했다.

### 앱으로 운영해도 되는가?

**소규모 운영에서 한 건씩 검토·처리하는 현재 범위에는 적합하다.** 신고 근거 확인, 회원 제재, 게시물 숨김, 공지 작성은 모바일 목록→상세→확인 흐름으로 처리할 수 있다. 서버가 권한·감사·동시성을 보장한다면 PC 웹이 아니어도 된다.

- 앱에 적합: 개별 신고 처리, 긴급 숨김, 회원 상태 확인, 제재/해제, 간단한 공지, 요약 통계.
- 모바일에서 불편한 부분: 긴 감사 이력 비교, 대량 회원 처리, 복잡한 통계 분석, 많은 카테고리 순서 조정.
- 이번 범위는 일괄 제재·CSV 추출·대량 삭제를 넣지 않고 한 건씩 처리한다. 긴 목록은 서버 필터와 페이지 조회로 줄인다.
- 화면 크기 때문에 중요한 사유/근거를 생략하지 않는다. 조치 확인 화면에서 대상·영향·기간을 모두 다시 보여준다.
- 나중에 웹을 만들더라도 운영자 API와 정책을 공유하고 화면만 별도로 만든다.

아래 값은 모두 검토용 권장값이다. 자동으로 운영 정책에 적용하거나 결정 로그에 확정사항으로 기록하지 않는다.

| 확인할 항목 | 권장 기준안 | 바뀌면 영향을 받는 부분 |
|---|---|---|
| 운영 화면 플랫폼 | 기존 Android 설정 → 운영자 센터 | 화면 구조·프론트 기술 스택 |
| 역할 | 원본의 SUPER_ADMIN / ADMIN / MODERATOR 유지 | 메뉴와 버튼·서버 권한 |
| 기간 정지 | 1·3·7·30일 프리셋, 서버 시각 기준 | 제재 폼·만료 처리 |
| 영구 정지 | SUPER_ADMIN만 실행, 자동 제재 금지 | 권한·추가 확인 |
| 콘텐츠 삭제 | 운영상 소프트 삭제, 물리 삭제 버튼 없음 | 복구·개인정보 삭제 절차 |
| DM 신고 근거 | 신고 메시지와 이전/이후 최대 2개씩, 동일 대화만 | 근거 수집·미디어 권한 |
| 이의신청 | 제재당 접수 중 1건, 정지 중에도 전용 경로 제공 | 사용자 화면·제한 인증 |
| 개인정보·근거 보유기간 | 출시 전 별도 확정, 임의 기간으로 자동 파기하지 않음 | 삭제 작업·보안 정책 |

검토용 Mock 화면은 위 가정으로 제작할 수 있다. 실제 제재·민감정보 조회를 켜기 전에는 권한, DM 근거 범위, 개인정보 보유기간을 합의해야 한다. 법적 적합성을 이 문서만으로 판단하지 않는다.

아래는 코드 존재 여부이며, 운영자 실연동 완료를 의미하지 않는다.

| 영역 | 현재 상태 | 필요한 작업 |
|---|---|---|
| 운영자 화면 | `FitMatePrototypeApp.kt`의 `AdminScreen`은 고정 통계·메뉴 문구·광고 이동 데모 | 실제 목록/상세/폼으로 교체, 운영 영역의 광고 연결 제거 |
| 운영자 접근 | 설정에 개발용 운영자 데모가 있음 | 서버 권한으로 진입 결정; DebugOnly는 보안 장치가 아님 |

| 신고 상태 | RECEIVED/REVIEWING/RESOLVED/**DISMISSED** | 반려의 서버 값은 DISMISSED 유지, 원본 REJECTED와 혼용 금지 |
| 신고 대상 | USER/POST/COMMENT/DM_MESSAGE | POST는 커뮤니티로 한정, MATE_POST 추가 필요 |
| 신고 사유 | SPAM/HARASSMENT/HATE/SEXUAL/VIOLENCE/SELF_HARM/OTHER | NO_SHOW·IMPERSONATION 추가 제안; 현재 UI는 일부 사유를 OTHER로 전송 |

| 콘텐츠 | 커뮤니티는 deletedAt, 메이트는 모집 상태 enum 보유 | 운영 숨김/삭제 상태 별도 추가 및 조회·미디어 경로에 적용 |
| 카테고리 | `fitness_sports`의 isActive/displayOrder 및 조회 API 존재 | 관리 API·version·활성화 가능 범위 검증 필요 |
| 공지·감사·관리 계정 | 검토한 컨트롤러에 운영자 관리 API 없음 | 신규 개발 범위 |

### 3.1 기존 계약과 호환 원칙

- 기존 사용자의 API를 운영자가 타인 ID를 넣어 호출하는 방식으로 재사용하지 않는다. `/api/v1/admin/**`에 관리자용 DTO·권한·조회 정책을 둔다.
- 기존 enum 이름은 가능한 유지한다. 사용자 표시는 한국어 매핑으로 해결한다.
- MATE_POST/NO_SHOW/IMPERSONATION 확장은 Android 전송값, 서버 enum, DB CHECK, 대상 검증, 테스트를 함께 변경한다.
- 메이트의 현재 상태는 RECRUITING/FULL/CLOSED/CANCELED다. 원본 명세의 COMPLETED 등을 이번 관리자 구현 때문에 임의로 추가하지 않는다.
- 사용자가 이미 실행한 Flyway 파일은 수정하지 않는다. 작업 착수 시 최신 버전 다음 번호를 확인하여 신규 migration을 추가한다.

최고 권한도 개인 건강정보를 무제한 조회하는 권한은 아니다. 비공개 콘텐츠와 DM 근거는 유효한 신고와 업무 사유가 있을 때만 제한적으로 제공한다. 일반 콘텐츠 탐색에서 비공개 본문을 일괄 노출하지 않는다.

### 4.2 진입과 인증

1. 일반 로그인 후 일반 인증으로 조회 가능한 `GET /admin/access`에서 본인 운영자 자격·MFA 등록 여부만 확인한다.
2. 자격이 없으면 운영자 메뉴를 표시하지 않는다. 직접 경로 진입도 서버 403 처리.
3. 자격이 있으면 운영자 센터 진입 시 2단계 인증 화면으로 이동한다.
4. 비밀번호 재확인 + TOTP를 검증해 짧은 운영자 세션을 발급한다. 일반 사용자 토큰과 권한 범위를 구분한다.
5. 제안: 운영자 세션 15분, 영구 정지·권한 변경은 최근 5분 내 재인증. 서버가 만료와 재인증 필요 여부를 반환한다.
6. 운영자 권한 회수·계정 정지·로그아웃 시 해당 세션을 무효화한다. 역할 확인은 토큰에 오래 고정된 값만 신뢰하지 않는다.
7. 운영자 센터 종료 시 일반 앱으로 복귀한다. 일반 계정 로그아웃과 운영자 세션 종료를 구분한다.

- 최초 SUPER_ADMIN 지정은 운영 환경의 통제된 초기 설정 절차로 수행한다. 앱 가입/설정에서 누구나 승격하는 경로는 만들지 않는다.
- 마지막 활성 SUPER_ADMIN을 제거하거나 본인 계정을 제재하지 못한다. 다른 운영자 제재는 SUPER_ADMIN만 가능하다.
- MFA 등록: 신원 재확인 → 서버 발급 등록 challenge → 등록 확인 코드 검증. 복구 코드는 해시만 저장하고 재설정은 별도 복구 절차로 처리한다.
- 실패 횟수 제한·계정/기기별 속도 제한을 서버에서 적용한다. Mock OTP 성공을 실제 인증처럼 사용하지 않는다.

## 5. 화면 구성 — Android 기준안

운영자 센터는 일반 홈/메이트/커뮤니티/DM/프로필 탭과 분리한다. 위에는 뒤로가기·화면명·운영자 역할, 아래에는 **현황 / 신고 / 회원 / 콘텐츠 / 더보기** 5개 메뉴를 둔다. 더보기에서 공지·카테고리·운영 규칙·감사·시스템 현황·권한 관리에 진입한다.

- 작은 통계 카드, 검색창, 상태 필터 칩, 재사용 가능한 목록 행을 사용한다. 전체 페이지를 거대한 카드로 감싸지 않는다.
- 상세는 별도 페이지, 필터는 바텀시트, 제재/삭제 확정은 대상·효과·사유를 재확인하는 다이얼로그로 구분한다.
- 상태는 색뿐 아니라 문구로 표시한다. 모든 모드에서 하단 시스템 바 inset과 48dp 이상의 터치 영역을 확보한다.
- 서버 로딩 중에는 skeleton 또는 `—`를 사용한다. 0과 미집계를 구분하고 데모 통계를 대체값으로 사용하지 않는다.

## 6. 핵심 동작과 상태

### 6.1 신고 검토·처리

`RECEIVED → REVIEWING → RESOLVED 또는 DISMISSED`

1. 목록 선택 → 신고 상세와 근거 조회.
2. 검토 시작 → 담당자 지정 및 version 증가. 두 운영자가 동시에 시작하면 후속 요청은 409.
3. 조치 선택: 조치 없음/경고/콘텐츠 숨김/운영 삭제/기간 정지/영구 정지/메이트 마감. 서버가 대상·역할·현재 상태에 맞는 allowedActions 반환.
4. 사유 코드와 사용자 안내를 입력한다. 내부 메모와 사용자 안내는 별도 필드다.
5. 처리 확인 → 신고 결정·필요한 콘텐츠/회원 조치·감사 로그·통지 이벤트를 서버 트랜잭션으로 저장.
6. 성공 후 서버가 반환한 상태로 상세/목록/미처리 건수를 갱신한다. 다른 신고까지 자동으로 완료 처리하지 않는다.

- 반려는 `DISMISSED`로 전송하고 UI에는 “반려”로 표시한다. 사유 부족·중복 검토·위반 없음 등의 사유를 기록한다.
- 신고 대상이 이미 삭제되면 스냅샷과 이전 조치를 보여준다. “대상 없음” 때문에 앱이 죽거나 404를 0건으로 표시하지 않는다.
- 반복 클릭/타임아웃 재시도는 같은 멱등키를 사용한다. 응답 유실 시 자동으로 새 제재를 생성하지 않고 상태를 먼저 조회한다.
- 처리 완료 신고는 직접 덮어쓰지 않는다. 정정이 필요하면 취소/후속 조치를 새 이력으로 추가한다. 재개 절차는 백엔드 합의가 없으면 UI에 노출하지 않는다.
- 신고 접수 시 서버가 신고자가 해당 대상을 볼 자격이 있는지 확인하고 필요한 근거를 저장한다. 현재 단순 UUID 저장만으로는 DM 열람 권한을 부여할 수 없다.

### 6.2 DM·비공개 근거

- DM 전체 목록/회원별 대화 검색/무제한 페이징 화면은 만들지 않는다.
- 운영자는 `reportId`에 종속된 근거 API만 호출한다. 다른 대화 ID를 넘겨 확장하는 기능은 없다.
- 제안 범위는 신고 메시지 ±2개, 같은 대화의 메시지로 제한한다. 이미지도 신고 관련 미디어에 한해 짧은 권한 검사 경로로 제공한다.
- 신고자만 볼 수 있었던 원문은 일반 회원 상세로 복제하지 않는다. 열람 시 관리자·사유·reportId를 감사 기록에 남긴다.
- 근거 열람 자체가 감사 기록에 실패하면 민감 근거 응답도 실패시킨다.
- 신고 후 원문 수정/삭제와 보유기간 만료를 구분한다. 근거가 보존되지 않은 이전 신고는 “근거 없음”으로 표시하고 복원했다고 가정하지 않는다.

### 6.3 회원 제재·만료·이의신청

| 조치 | 계정 상태 | 추가 입력 / 규칙 |
|---|---|---|
| WARNING | ACTIVE 유지 | 사유·안내·연결 신고; 신고 수만으로 자동 정지하지 않음 |
| SUSPEND | SUSPENDED | 1/3/7/30일 중 기간, 시작은 서버 처리 시각 |
| BAN | BANNED | SUPER_ADMIN, 재인증, 사유 재확인 |
| REVOKE | 유효 제재를 재계산 | 해제 사유; WITHDRAWN 계정을 ACTIVE로 되살리지 않음 |

- 제재는 `user_sanctions` 제안 테이블에서 별도로 관리한다. 현재 계정 상태만 덮어쓰면 과거 이력과 만료를 알 수 없다.
- 기간 만료는 서버가 계산한다. 배치뿐 아니라 인증 검사에서도 만료를 확인하여 배치 지연 때문에 정지가 계속되지 않도록 한다.
- 정지/영구 정지는 기존 토큰·세션을 무효화한다. 해제 후에는 재로그인한다.
- 정지 후 글 작성·댓글·DM·참가 신청을 차단한다. 기존 모집은 신규 신청을 막고 정리 필요 상태를 표시하되, 참가자들의 개인 운동 기록을 강제로 삭제하거나 종료하지 않는다.
- 이의신청 상태: `RECEIVED → REVIEWING → ACCEPTED 또는 REJECTED`. 신고 반려의 DISMISSED와 별개 도메인이다.
- **현재 인증 필터는 SUSPENDED/BANNED 사용자의 요청을 차단하므로 일반 로그인 뒤 이의신청을 넣는 설계만으로는 동작하지 않는다.** 비밀번호로 본인 확인 후 이의신청에만 쓸 수 있는 제한 세션을 발급하는 별도 경로를 추가한다.
- 제한 세션은 본인 제재 안내·이의신청 생성/조회만 가능하며 일반 API와 운영 API에서는 거부한다. 이메일 존재/제재 여부를 비인증 상태에서 노출하지 않는다.
- 인용하면 해당 제재를 해제하는 별도 이력을 만들고 다른 유효 제재를 재계산한다. 기각은 유지 사유를 사용자에게 통지한다.

### 6.4 콘텐츠 조치

- 제안 운영 상태: `VISIBLE / HIDDEN / REMOVED`. 기존 `PUBLIC/MUTUAL`, `deletedAt`, 메이트 모집 상태와 독립이다.
- 숨김: 사용자 피드/검색/상세/알림 링크/미디어에서 비노출. 작성자는 사유 안내를 볼 수 있다.
- 운영 삭제: 사용자 관점에서는 삭제되지만 즉시 물리 삭제하지 않는다. 근거 보유와 개인정보 파기는 별도 정책이다.
- 복구: 운영 조치만 해제한다. 작성자가 삭제했거나 탈퇴 정리 대상인 콘텐츠를 되살리지 않는다.
- 댓글 숨김 시 답글이 있으면 “운영 정책에 따라 숨겨진 댓글” 자리표시자를 사용할 수 있다.
- 메이트 마감은 새 신청을 막는 CLOSED 처리이며 기존 수락자 취소와 다르다. 모임 전체 취소가 필요하면 별도 취소 동작으로 참가자 통지까지 수행한다.
- 메이트 숨김/삭제 중 신규 신청·수락을 차단한다. 기존 확정자에게는 원문/미디어가 아닌 “운영 조치로 중단된 모임” 안내와 취소 동작만 허용한다. 개인 운동 기록은 유지한다.

### 6.5 공지·카테고리·규칙

**공지**

- 상태: DRAFT/SCHEDULED/PUBLISHED/ENDED. 상태는 서버 시각으로 결정하며 프론트가 임의 게시 처리하지 않는다.
- 제목 1~100자, 본문 1~5,000자, 대상 ALL/REGION/SPORT, 지역·종목 ID 목록, 시작·종료 시각, pinned, version을 사용한다.
- 시작 < 종료, 예약은 미래 시작, 즉시 게시는 서버 현재 시각 사용. 편집기 미리보기와 사용자 실제 표시 형식을 맞춘다.
- 일반 사용자의 공지 목록·상세 화면과 긴급 공지 진입 배너도 필요하다. 광고 영역으로 재사용하지 않는다.
- Push는 기존 전송 기반 확인 전 완료로 표시하지 않는다. 우선 실제 인앱 노출·목록을 계약하고 Push 여부는 별도 capability로 표시한다.

**카테고리**

- 기존 서버 종목 ID/code는 변경하지 않는다. 비활성화는 신규 선택에서 제외하며 기존 게시물·루틴·기록의 이름과 조회는 보존한다.
- `HEALTH/RUNNING`과 다른 종목의 기능 지원 범위가 다르다. 단순 isActive 변경으로 미지원 개인 운동 흐름을 열지 않는다.
- 관리 응답에 supportedContexts(예: MATE/SOLO), canDeactivate, disabledReason을 추가 제안한다. 실제 범위 분리 전에는 안전하게 변경 가능한 종목만 조작한다.
- 순서는 전체 ID와 version을 한 번에 제출해 원자적으로 저장한다. 중복/누락을 거부한다.
- 기타 운동 입력은 정규화 이름과 사용 건수만 집계한다. 사용자 식별정보는 포함하지 않는다. “정식 종목 승격”은 서버 코드 enum 변경이 필요하므로 이번 화면에서 자동 실행하지 않는다.

**금칙어·스팸**

- 초기에는 작성 시 경고 또는 검토 후보 표시만 사용한다. 자동 계정 정지·대량 삭제는 금지한다.
- 규칙 종류: 단어 일치/동일 내용 반복/시간 구간별 과다 작성. 적용 영역은 공개 커뮤니티·댓글·메이트로 제한한다.
- DM 전체 내용 수집·분석은 포함하지 않는다. 전송 횟수 제한은 내용 감시와 별도의 서버 rate limit이다.
- 규칙 변경에는 사유·활성 여부·version·변경 이력이 필요하다. 임의 정규식·실행 스크립트 입력은 허용하지 않는다.

## 7. 대시보드·장애 현황의 숫자 정의

기본 표시 구간은 KST 오늘 00:00~현재이며 저장·API 시간은 UTC ISO-8601이다. 기간 끝은 미포함 `[from,to)`로 통일하고 `asOf`, `timezone`, 각 지표의 availability를 반환한다.

| 지표 | 정의 / 주의 |
|---|---|
| 전체/신규 회원 | 탈퇴 제외 전체 수 / 선택 기간에 가입한 수; 상태별 집계는 별도 |
| DAU/WAU/MAU | 기간 중 유효 활동 이벤트가 있는 고유 사용자 수. 로그인 횟수나 전체 회원 수로 대체하지 않음 |
| 커뮤니티/메이트 게시물 | 기간 내 생성 수, 운영 숨김 수 별도; 모집 완료와 혼동 금지 |
| 운동 완료 | 완료된 헬스 세션 + 러닝 기록 수; 중복 동기화 기록을 재집계하지 않음 |
| 대기 신고 | RECEIVED + REVIEWING 건수; 기간별 접수 수와 구분 |
| OCR 실패율 | 기간 내 판독 종료 요청 중 FAILED / (COMPLETED+REVIEW_REQUIRED+FAILED); 분모 0이면 비율 null |
| 서비스 오류 | 서버 요청 실패 집계, 기간·endpointGroup·statusClass·requestId 요약. 원문 로그·키·본문 제외 |

활동 이벤트/오류 집계 기반은 아직 확인되지 않았다. 구현 전까지 `availability=UNAVAILABLE`, `value=null`로 표시한다. 프론트 Mock은 수치에 “데모”를 명시하고 실제 서버 실패 시 Mock으로 대체하지 않는다. OCR 현황은 상태·오류 코드·지연 시간만 보여주며 체성분 수치와 원본 이미지는 노출하지 않는다.

## 8. 프론트 구현 구조와 Mock 계약

### 8.1 권장 경계

```text
운영 화면 → 화면별 ViewModel/UiState → AdminRepository
                                      ├─ FakeAdminRepository (개발/프리뷰 전용)
                                      └─ RemoteAdminRepository (서버 연동)
```

- 기존 `AdminScreen` 안에 모든 기능을 계속 추가하지 않는다. admin/navigation, ui, model, repository로 책임을 나눈다.
- UI 모델과 서버 DTO를 분리하고 enum/날짜/마스킹/allowedActions 매핑을 repository 경계에서 한다.
- 사용자 계정 데이터와 운영자 데이터 캐시는 분리한다. 운영자 로그아웃/권한 변경 시 운영 캐시·근거 이미지를 폐기한다.
- Fake/Remote 선택은 개발 빌드 주입으로만 한다. 실사용 앱에서 Fake 버튼으로 권한을 얻거나, 네트워크 실패 시 자동으로 Fake로 전환하지 않는다.
- Mock 구현도 실제 계약처럼 페이지·검색·필터·상태 전환·버전 충돌·권한 거부를 처리한다. 단순 Text/Toast 교체로 완료 처리하지 않는다.

### 8.2 필수 상태

`InitialLoading / Content / Empty / Refreshing / LoadError / Submitting / SubmitUnknown / PermissionDenied / SessionExpired / VersionConflict`

- 목록 0건과 조회 실패를 구분한다. 새로고침 실패 시 이전 데이터에는 마지막 갱신 시각을 표시한다.
- 저장 중 중복 버튼 비활성화. 실패 시 입력 보존. 재시도 성공 여부가 불명확하면 조회로 확인한다.
- 401/운영 세션 만료는 추가 인증, 403은 권한 안내, 409는 최신 상세 재조회 후 재검토. 자동 재제재 금지.
- 저장 결과 화면에는 처리 번호와 최신 상태를 보여준다. 서버 확정 전 카운트나 회원 상태를 확정값처럼 바꾸지 않는다.

### 8.3 Mock 시나리오

실제 사람·대화·건강정보를 복사하지 않는다. 데이터는 명백한 가상값으로 만든다.

| 도메인 | 최소 fixture |
|---|---|
| 회원 | 정상·기간 정지·영구 정지·탈퇴·운영자 각 1명 이상 |
| 신고 | USER/POST/COMMENT/DM_MESSAGE/MATE_POST 각 1건 이상; REVIEWING/반려/완료/근거 없음 포함 |
| 콘텐츠 | 공개·맞팔 공개·숨김·삭제·마감된 메이트 |
| 이의신청 | 접수·검토·인용·기각·기존에 해제된 제재 |
| 공지 | 초안·예약·게시·종료·긴급 고정 |
| 카테고리 | 활성·비활성·필수 비활성 불가·정렬 충돌·기타 종목 집계 |
| 공통 실패 | 401/403/409/429/500, 응답 지연, 저장 성공 후 응답 유실 |

## 9. 백엔드 전달용 공통 API 계약안

**이 절의 `/admin/**`와 이의신청/공지 조회 경로는 신규 제안이며 현재 구현된 API가 아니다.** 기존 `POST /api/v1/reports`, `/auth/**`, `/sports`와 공통 응답 외에는 연동 완료로 표시하지 않는다.

- 기존 `ApiResponse`, `CursorPageResponse`, `ErrorResponse`를 따른다. 성공 `{data:...}`, 실패 `{error:{code,message,fields:[]}}`.
- 목록: `cursor`는 opaque 문자열, `size` 기본 20/최대 50. 응답 `items,nextCursor,hasNext`. 필터/정렬 변경 시 cursor 초기화.
- 기본 정렬 `createdAt DESC,id DESC`. 날짜는 UTC ISO-8601, ID는 UUID 문자열, 표시명 대신 ID로 조치한다.
- 변경 요청에 `expectedVersion` 필수. 대상 조합 처리에는 신고 version과 대상 version을 모두 확인한다. 처음 version은 서버가 정한다.
- 제재·신고결정·공지게시·모집마감 등 동작 요청에는 `Idempotency-Key` 필수. 같은 관리자/경로/키/본문은 동일 응답, 같은 키에 다른 본문은 409.
- reasonCode(서버 제공 enum), publicReason(1~500자), internalNote(선택, 최대 1,000자)를 분리한다. 오류 message만으로 로직을 분기하지 않는다.
- 모든 조작은 서버가 역할·대상·현재 상태를 재검증한다. `allowedActions`는 UI 힌트이지 보안 검사를 대신하지 않는다.
- 내부 메모, 신고자 식별정보, 민감 근거는 대상 회원에게 반환하지 않는다.

### 9.4 예시 — 신고 검토 후 숨김 처리

식별자는 전부 가상 예시다. 필수 header: 운영 인증, `Idempotency-Key`.

```json
{
  "expectedVersion": 3,
  "targetVersion": 8,
  "resolution": "RESOLVED",
  "action": "HIDE",
  "reasonCode": "HARASSMENT",
  "publicReason": "운영 정책 위반으로 게시물이 숨김 처리되었습니다.",
  "internalNote": "신고 근거와 게시물 내용을 확인함"
}
```

서버는 신고 대상과 action 조합을 검사하고 변경을 한 번만 실행한다. 성공 응답에는 `data.report`, `data.actionId`, `data.affectedResources`를 반환한다. 회원 제재가 없었는데 “회원 정지 완료” 같은 문구를 표시하지 않는다.

| HTTP / 오류 코드 제안 | 프론트 처리 |
|---|---|
| 401 INVALID_ACCESS_TOKEN / ADMIN_SESSION_EXPIRED | 일반 또는 운영 인증 화면으로 구분 이동 |
| 403 ADMIN_PERMISSION_REQUIRED / REAUTH_REQUIRED | 권한 없음 또는 재인증; 데이터 유지 범위 제한 |
| 404 RESOURCE_NOT_FOUND | 대상 소멸 안내, 목록 갱신 |
| 409 VERSION_CONFLICT / ALREADY_PROCESSED / IDEMPOTENCY_CONFLICT | 최신 상세 조회·기존 결과 확인, 자동 조치 금지 |
| 400 VALIDATION_ERROR / INVALID_STATE_TRANSITION | fields 기반 입력 오류 또는 상태 안내 |
| 429 RATE_LIMITED | 재시도 가능 시각 안내 |
| 500 INTERNAL_ERROR | 성공 처리하지 않음, 요청 식별자로 운영 확인 |

기존 서버에 없는 오류 코드는 신규 합의 대상이다. 현재 공통 ErrorResponse 형태를 깨지 않고 확장한다.

## 10. 백엔드 구현 책임과 DB 변경 개요

SQL 확정본이 아니라 저장 책임 제안이다. 기존 테이블 이름/타입/인덱스는 백엔드가 검토한다.

| 영역 | 저장할 정보 / 유의사항 |
|---|---|
| 운영자 권한·세션 | userId, role, enabled, MFA 등록 상태, 권한 변경 이력, 운영 세션 만료/회수; TOTP 비밀 암호화·복구 코드 해시 |
| user_reports 확장 | 담당자, version, 결정/사유/일시. 현재 신고 사유 CHECK와 enum을 함께 확장 |
| report_evidence | reportId 기반 최소 근거, 원문 버전·보유기한·접근 통제; 일반 응답/로그에 본문 유출 금지 |
| moderation_actions | 대상, 조치, 사유, 취소 연결, 작업자, 멱등키, version; 원래 콘텐츠 상태와 분리 |
| user_sanctions | 종류, 기간, 현재 유효 상태, 연결 신고, 공개 사유/내부 메모, 해제 이력 |
| sanction_appeals | 제재 연결, 본인 요청, 담당자, 심사 상태·결과·시각·version |
| notices | 본문, 대상, 기간, 상태, 고정, version |
| 운영 규칙 | 구조화된 조건·활성 상태·버전, 규칙 결과 요약; 원문 대량 보관 금지 |
| admin_audit_logs | 변경 전후 비민감 요약, 작업자, 사유, requestId, 결과; 수정/삭제 API 없음 |
| erasure_jobs | 승인된 삭제 범위·진행·오류·재시도; 완료 후 복구 버튼 제공 금지 |
| 통계 | 활동 이벤트/일별 집계와 오류 집계 필요. 기존 데이터만으로 계산 가능한 항목과 구분 |

- 상태 변경과 감사 로그는 같은 트랜잭션, 사용자 통지는 outbox 또는 동등한 신뢰성 있는 이벤트로 전달한다. 알림 실패로 제재를 중복 실행하지 않는다.
- 알림 수신자가 앱을 다시 열면 최종 결과를 조회할 수 있어야 한다. 인앱 알림 본문에는 내부 메모·신고자 신원·DM 원문을 넣지 않는다.
- 운영 숨김 조건은 목록뿐 아니라 상세/이미지/첨부/검색/참가 신청/알림 deep link까지 적용한다.
- 본문·검색 키워드·이메일·인증 정보가 일반 접근 로그에 그대로 남지 않도록 검토한다.
- 중복/동시 처리, 마지막 SUPER_ADMIN 회수 방지, 본인 제재 방지는 프론트 버튼뿐 아니라 서버/DB에서도 검증한다.
- 감사 기록 정정은 새 이벤트로 남긴다. 보유기간에 따른 파기 작업도 권한과 감사를 갖는 별도 작업으로 취급한다.

## 11. 개발 순서와 전달 기준

날짜는 정하지 않는다. 아래는 **의존성 기반 작업 순서**이며 원본 제품의 개발 일정 확정을 의미하지 않는다.

| 단계 | 프론트 작업 | 완료 기준 / 백엔드 전달물 |
|---|---|---|
| F0 | 플랫폼·권한·핵심 상태 검토 | 이 문서의 가정에 사용자 확인, 용어·enum 합의 |
| F1 | 운영 진입·추가 인증 화면·공통 UI·Fake repository | 역할별 진입/403/만료/로딩/오류 시연; 실제 권한 구현으로 표기하지 않음 |
| F2 | 신고 목록/상세·근거·콘텐츠 조치 | 접수→검토→숨김/반려→목록 갱신; 취소·중복·409 시나리오 |
| F3 | 회원 제재·해제·이의신청과 사용자 안내 | 기간/영구 정지·권한 차이·정지 중 이의신청 Mock 시연 |
| F4 | 공지·사용자 노출·카테고리·규칙 | 생성/수정/기간/정렬/비활성 시나리오 |
| F5 | 대시보드·장애 현황·감사·운영자·삭제 작업 상태 | 수집 불가와 0 구분, 민감정보 미노출 |
| H1 | 검토한 화면을 계약 문서와 묶어 전달 | DTO 타입/null/enum/예시, API 목록, 오류, 권한표, 전이표, fixture, 테스트 체크리스트 |
| B1 | 백엔드 역할/MFA/세션·감사 공통 기반 | 401/403·권한 회수 검증 후 첫 연동 가능 |
| B2 | 신고→근거→조치→제재→사용자 결과 | 모듈별 Remote repository 교체, Fake 자동 fallback 금지 |
| B3 | 공지·카테고리·규칙·집계·삭제 작업 | 화면별 실제 DB 왕복 검증 후 연동 완료 표기 |

프론트 먼저 만든다는 것은 **서버 권한/계약을 나중에 즉흥적으로 정한다는 뜻이 아니다.** F0에서 초안을 공유하고 H1에서 실제 화면과 계약 차이를 최종 확정한다. 계정 정지 필터·메이트 상태·DM 근거 같은 부분은 백엔드가 먼저 계약 위험을 검토해야 한다.

백엔드에 넘길 때 각 API를 `제안 / 합의 / 서버 구현 / 프론트 연동 / 실기기 검증`으로 관리한다. 화면 완성을 서버 구현 완료로 바꾸지 않는다. 확정된 결정·Action Item은 기존 [결정·회의 로그](../00-project/결정-회의-로그.md)의 존재와 내용을 확인한 후 그 문서에 기록한다.

## 12. 인수 기준과 시연 순서

### 필수 검증

- [ ] 일반 계정이 메뉴/직접 API/미디어 URL을 통해 운영자 권한을 얻지 못한다.
- [ ] 운영자 MFA 만료·권한 회수 후 기존 운영 세션이 거부된다.
- [ ] 역할별 allowedActions와 서버 거부 결과가 일치한다.
- [ ] 신고 근거는 접근 자격이 검증된 해당 신고 범위만 반환한다.
- [ ] 일반 DM·인바디 원본·개인 경로가 모든 역할에서 노출되지 않는다.
- [ ] 반려는 DISMISSED로 왕복하고 메이트 신고는 MATE_POST로 분리된다.
- [ ] 동일 신고/회원 동시 조치에 409, 반복 요청에는 중복 제재/알림이 없다.
- [ ] 제재 만료/해제 이후 상태가 올바르고 WITHDRAWN은 복구되지 않는다.
- [ ] 정지 회원이 제한 경로로 이의신청할 수 있지만 일반 기능은 사용할 수 없다.
- [ ] 숨김/삭제가 목록·상세·미디어·deep link에 모두 적용된다.
- [ ] 메이트 강제 마감이 수락자의 개인 운동 기록을 삭제하지 않는다.
- [ ] 공지 예약/종료가 서버 시각과 사용자 대상 조건대로 적용된다.
- [ ] 카테고리 비활성화 후 기존 기록이 깨지지 않는다.
- [ ] 성공 조치에 감사 로그가 있고 로그에 민감 본문/인증 값이 없다.
- [ ] 로딩·0건·집계 불가·조회 오류가 구분되며 데모 값이 실제 화면에 잠깐 나타나지 않는다.
- [ ] 운영자 처리 후 일반 사용자 앱에서 결과를 실제 서버 데이터로 확인한다.

### 권장 시연

1. 일반 계정에는 운영자 진입이 없음을 확인.
2. 운영 계정으로 추가 인증 → 대기 신고 목록.
3. 신고 근거 확인 → 게시물 숨김 → 감사 기록 확인.
4. 일반 사용자에서 해당 게시물 비노출·신고 처리 결과 확인.
5. 기간 정지 → 제한된 이의신청 → 인용/해제 → 재로그인.
6. 공지 게시 → 일반 사용자 공지 확인.
7. 실제 연동 전이면 모든 시연에 Mock임을 명시한다.
