## 1. 문서의 사용 방법

이 문서는 확정 API 명세나 전체 API 구현 완료 보고가 아니다. 현재 UI에서 필요한 데이터를 역으로 정리한 연동 검토안이다. 기존 API 경로·DTO는 가능한 재사용하고, 새 경로와 새 필드는 백엔드 검토 후 확정한다. UI의 한국어 문자열이나 로컬 저장 구조를 그대로 서버 스키마로 채택하지 않는다.

각 항목은 `화면/사용자 행동 → 입력값 → 필요한 응답 → 상태/오류 → 서버 구현 상태 → 확인사항` 순서로 상세화한다. 최종 계약은 필드별 타입·필수 여부·null·단위·제약·예시 JSON까지 채워야 한다. 아래의 신규 영역 데이터명은 의미를 설명하기 위한 제안이며 확정 DTO가 아니다.

## 2. 현재 진행 상태: 문서와 실제 main을 구분

| 영역 | 프론트 | 서버 main 코드 확인 | 의미 |
|---|---|---|---|
| 가입·로그인·토큰 | 로컬 데모 계정 흐름 | AuthController 및 AuthService 있음 | HTTP 연동과 실제 환경 검증 필요 |
| 내 프로필·커스텀 종목 | 입력·편집·로컬 저장 | ProfileController 및 DTO/Service 있음 | ID·enum·version 매핑 필요 |
| 약관·지역·시설·비밀번호 변경·탈퇴·알림 설정 | 관련 UI 있음 | main에 해당 Controller 없음 | Backend A 하위 브랜치 코드 통합 필요 |
| 종목·운동 사전 | 정적 종목·운동 가이드 | FitnessQueryController 있음 | 서버 사전 ID로 교체 |
| 루틴·세션·세트·리포트 | 상태 전환·기록·리포트 UI 있음 | Entity 중심, 해당 REST Controller 없음. WorkoutReportService는 메서드 없는 interface | P0 문서가 있어도 구현 완료는 아님 |
| 러닝 | GPS 서비스·랩·기록 UI | 전용 API 없음 | 기기 측 수집과 서버 저장 계약 분리 |
| 메이트 모집·문의·신청·알림 | 로컬 Mock 상태 및 저장 | 모집글·문의 채팅·신청·인앱 알림 API 구현 및 MySQL HTTP 통합 검증 완료 | [P1 메이트 API 명세](./p1-mate-api-명세.md)로 DTO·오류·페이지 계약 적용 |
| 인바디 | 사진 선택/촬영·검수·수동 입력·기록 | 업로드/OCR/기록 API 없음 | 실제 촬영과 실제 판독을 구분 |
| Samsung Health | SDK 조회 및 참고 리포트 | 로그 저장·매칭 API 없음 | 기기 로그와 세션 매핑 필요 |
| 관리자·광고 | 이 검토에서 운영 화면 완성 확인 안 됨 | 해당 API 없음 | 모바일 연동 범위와 운영 정책 별도 검토 |

**Backend A 병합 주의:** PR #20/#21은 하위 브랜치로 merge됐지만 해당 MemberController는 현재 main에 없다. `origin/codex/backend-a-p0-auth`에는 존재한다. 이 Controller의 `GET /users/me`, `PATCH /users/me/profile`은 main의 ProfileController와 경로가 중복되고, 수정 응답 타입도 다르다. 그대로 병합하면 중복 매핑 및 계약 충돌 위험이 있으므로 프로필 API를 하나로 통합하고 PR #23의 customSports 동작을 보존해야 한다.

메이트 범위는 Docker MySQL에서 Flyway V5→V8 업그레이드와 HTTP 통합 테스트를 수행했다. Android 실제 화면 연동은 API 예제와 이 문서의 매핑을 기준으로 별도 확인한다.

## 3. 공통 데이터·통신 계약

| 주제 | 적용/합의 내용 |
|---|---|
| 기존 공통 형식 | `/api/v1`, Bearer 인증, `{data: ...}` 응답과 기존 오류 포맷 재사용. 204는 본문 없음 |
| ID | 서버 UUID는 Android에서 String으로 보관. 로컬 Long ID, 이름, 리스트 index를 서버 식별자로 사용하지 않음 |
| 날짜 | 생일·측정일은 날짜 값, 운동/메시지 시각은 timezone이 명확한 timestamp. `오늘 19:30`, `HH:mm`은 화면에서 생성 |
| 단위 | 계약에 kg/lb, m/km, 초/분, 초/km, kcal, bpm을 명시. 서버 기준 단위와 UI 단위 변환은 분리 |
| 누락 | 외부 측정값 미제공은 null/누락, 실제 0과 구별. 빈 목록은 [] |
| 페이징 | 기존 `data.items` 구조에 next cursor와 종료 조건 확정. 현재 운동 사전 cursor는 페이지 index 문자열 구현 |
| 변경 충돌 | 프로필의 version은 기존 계약 사용. 다른 자원의 version 적용 범위는 API별 명시 |
| 중복 요청 | 기존 문서의 인증된 생성 요청 Idempotency-Key 정책은 구현 여부 확인 필요. 신규 생성/재전송은 같은 요청 ID로 중복 방지, 가입은 기존 예외 유지 |
| 인증 만료 | 동시 401에도 refresh는 하나로 합치고 요청 1회 재시도. 갱신 실패는 재로그인 |
| 권한 | 본인/작성자/참가 확정자/맞팔/차단 여부를 서버가 판정. 버튼 숨김만으로 권한을 보장하지 않음 |
| 로컬 저장 | Mock 데이터와 실제 계정 데이터를 구분. 기존 예시 데이터를 서버로 자동 업로드하지 않음. 초안·대기 요청은 사용자별 분리 |
| 실시간 | DM·읽음·알림은 polling/WebSocket 등 전달 방식, 재연결·누락 복구 계약 필요. Push는 별도 기능 |

## 4. 화면별 API와 필요한 값

아래 경로는 `/api/v1` 기준이다. `기존 문서`는 구현 확인을 의미하지 않는다. 경로가 없는 항목은 기능 요구만 제시하며 백엔드가 경로를 제안한다.

### 4.1 가입·로그인·프로필·설정

| 행동 | API / 상태 | 입력·필요 응답 |
|---|---|---|
| 이메일·닉네임 중복 확인 | GET /auth/email-availability, /auth/nickname-availability / main 있음 | email 또는 nickname → value, available |
| 가입 | POST /auth/signup / main 있음 | 아래 매핑 표와 기존 SignUpRequest 참고 → user, tokens |
| 로그인·갱신·로그아웃 | POST /auth/login, /refresh, /logout, /logout-all / main 있음 | 기존 AuthDtos 사용, 로그인 응답 userId와 가입 응답 user.id가 다름 |
| 프로필 조회·편집 | GET /users/me, PATCH /users/me/profile / main 있음 | 기존 ProfileDtos. 수정에는 version 필수, 응답은 최신 MyProfileResponse |
| 약관·지역·시설 조회 | GET /terms, /regions, /facilities / 하위 브랜치 | 문서 ID·유형·필수·버전·본문 링크, 지역 ID·이름·상위 ID, 시설 ID·이름 |
| 동의·비밀번호·탈퇴·알림 설정 | 기존 P0 문서 §6~7 / 하위 브랜치 | 동의 문서 ID, 비밀번호 재확인, 설정 bool과 version. 실제 데이터 삭제 완료와 계정 탈퇴 상태 구별 |
| 이메일 인증·비밀번호 찾기 | 신규 계약 필요 | 이메일 발송, 만료·재발송 제한, 인증 결과·재설정 수단. v1.2 요구이나 기존 P0 제외 |
| 프로필 사진 | 신규 업로드 계약 필요 | 기기 URI → 업로드 mediaId → 프로필 이미지 참조 및 표시 URL |

| 현재 프론트 값 | 기존 서버 필드 | 차이/처리 |
|---|---|---|
| nickname, displayName, email, birthDate, bio | 동명 필드 | 표시 날짜를 ISO 날짜로 변환. password confirmation은 UI 검증 전용 |
| isPrivate | visibility | PUBLIC/PRIVATE 변환 |
| region 문자열 | activityRegionIds[] | 지역 검색·선택 시 ID 보관 필요 |
| facilityName | facilityNames[] | 현재 단일 입력을 배열로 매핑. 서버는 시설 입력 시 활동 지역 정확히 1개 요구 |
| interests의 FITNESS | sports[].sportCode=HEALTH | 헬스 코드 차이. 나머지 종목도 서버 사전과 명시 매핑 |
| experience 한국어 단일 값 | sports[].skillLevel | 서버는 종목별 경력. 입문→BEGINNER 등 매핑 및 UI 단일 경력 적용 범위 합의 |
| customInterests 문자열 집합 | customSports:[{name}] | 생략/null 유지, [] 삭제, 배열 교체의 기존 계약 유지 |
| goals 문자열 집합 | goals:[{goalCode,primary}] | 서버는 primary 정확히 1개 요구. 현재 주 목표 별도 선택이 필요 |
| availableTime 자유 문자열 | availableTimes:[{weekdayLocal,startLocalTime,endLocalTime,timezoneId}] | 자유 문장을 추측 변환하지 말고 구조화 입력·표시 매핑 합의 |
| isAdultVerified, 동의 체크 | consentDocumentIds 등 | 연령 확인과 법적 동의 기록은 구별. 서버 연령 정책·동의 문서 연결 필요 |

현재 서버는 가입 시 HEALTH를 정확히 1개 포함하도록 검증한다. 러닝만 선택하는 프론트 흐름과 충돌한다. 추천안은 사용자의 실제 관심 종목을 허용하고 헬스 관련 기능 진입 시 필요한 경력을 받는 방식이며, 확정 정책은 아니다.

### 4.2 홈·운동 기록 탐색

필요 응답: 사용자 요약, 운동 이력/요약, 루틴, 메이트 모집 목록, 피드, 미확인 알림·DM 수. 프로필 통계는 게시물/운동 기록/팔로워/팔로잉 수와 현재 조회자의 권한을 포함한다.

집계 기준(완료 세션만 포함, 예시 제외, 주간 시작일·시간대)을 정의한다. 홈 전용 집계 API를 신설할지 기존 조회를 조합할지는 백엔드가 제안한다. 단순 화면 조합을 위해 반드시 새로운 API를 만들 필요는 없다.

### 4.3 운동 사전·루틴·공통 운동·리포트

| 행동 | 기존 경로 / 상태 | 화면에서 필요한 값·추가 계약 |
|---|---|---|
| 운동 검색·설명·대체 | GET /sports, /exercises, /exercises/{id}, /exercises/{id}/substitutions / main 있음 | exerciseId, 이름, 부위, 장비, 설명·이미지·영상 nullable, 대체 운동 ID |
| 추천·템플릿·저장 루틴 | GET /routines/recommended, /templates, /routines, /routines/{id} / 기존 문서 | routineId, 출처, 이름, 목표·난이도, 예상 시간, 순서별 exerciseId·목표 세트/반복/중량/휴식, version |
| 루틴 생성·편집·삭제 | POST /routines, PATCH/DELETE /routines/{id} / 기존 문서 | 이름·운동 항목·순서, 참조 템플릿 ID, version. 프론트는 현재 운동명을 저장하므로 ID 추가 필요 |
| 개인 세션 생성 | POST /workout-sessions / 기존 문서 | sportCode, entryType, routineId, useSamsungHealth. MATE는 모집/참가 연결 ID 추가 검토 |
| 시작·정지·재개·완료·취소 | POST /workout-sessions/{id}/{start,pause,resume,complete,cancel} / 기존 문서 | timestamp·경과/활동 시간·version·취소 사유 → 확정 상태·시간·version |
| 운동 구성 변경 | 세션 exercises POST/PATCH/DELETE / 기존 문서 | sessionExerciseId, exerciseId, 순서, 이름 스냅샷. 같은 운동을 두 번 넣어도 독립 ID 필요 |
| 세트 저장·수정 | PUT /workout-sessions/{id}/exercises/{id}/sets/{setNo} / 기존 문서 | 중량·반복·완료·RPE·메모·휴식·version·clientUpdatedAt. 정확한 기존 필드명은 P0 §10.6 기준 |
| 세트 삭제 | 기존 세트 DELETE 경로 없음 | 현재 UI는 삭제 지원. 삭제 식별자, 이후 번호 재정렬, 리포트 재계산 필요 |
| 이전 기록·리포트 | GET /exercises/{id}/previous-record, /workout-sessions/{id}/report / 기존 문서 | 총 시간·세트·반복·볼륨, 운동별 요약·목표 달성, 세트 RPE/메모, 비교 대상 ID·시점·차이 |
| 이력·복원 | GET /workout-sessions, /workout-sessions/{id} / 기존 문서 | 완료 기록과 미완료 세션 구분, 중단 시 저장·재시도·다른 기기 변경 처리 |

프론트의 WorkoutSet은 exerciseName 중심이며 세트/세션 ID가 없다. 서버 DTO를 별도로 두고 UI 모델로 변환해야 한다. 휴식 카운트다운·애니메이션은 기기에서 실행하고, 서버는 복원에 필요한 시각·상태·기록을 저장한다.

v1.2의 세션 상태 READY/IN_PROGRESS/PAUSED/SYNC_WAITING/REVIEW_REQUIRED/COMPLETED/CANCELED를 기준으로 계약을 맞춘다. 기본 리포트가 존재하면서 외부 로그를 기다리는 상태의 표현도 합의한다.

### 4.4 러닝·Samsung Health

| 영역 | 전송할 값 | 받아야 할 값 / 미확정 |

| 러닝 결과 | 활동 시간·거리, 랩 번호/거리/시간, RPE·컨디션·메모, 완료 시각 | 평균/최고 페이스, 목표 달성, 이전 기록·개인 최고 비교, 외부 값 nullable |
| GPS 복원 | 임시 세션 ID·마지막 저장 시각·누적 거리·활동 시간 | 중단/복원 규칙. 매 GPS sample을 HTTP로 전송할 필요는 없음 |
| Samsung 원본 | uid, sourceAppId, 운동 유형, 시작/종료, 기기, 제공된 거리·칼로리·심박·속도·고도·케이던스 등 | 저장 레코드 ID, 중복 처리, 매칭 후보, 연결 상태, 리포트 갱신 상태 |
| 연결·해제·삭제 | 계정 동의 및 세션별 사용 여부, 연결할 외부 기록 ID | 연결 해제와 서버 보관 데이터 삭제는 별도 결과·상태로 제공 |

실제 로그는 워치/Samsung Health 종료 → 휴대폰 SDK 조회 → 앱이 서버에 전송하는 흐름이다. 서버가 워치를 직접 시작/종료시키는 계약은 아니다. 후보가 여러 개면 사용자 선택, 로그가 없으면 기본 리포트 유지가 필요하다.

현재 Samsung UI 모델에는 원본 수정 시각이 없다. v1.2 중복·수정 처리에 필요한 원본 수정 시각의 SDK 획득 가능 여부를 확인하고, 미제공 시 대안을 합의한다. 현재 GPS는 경로 좌표 저장/지도 표시까지 구현된 것으로 보지 않는다. v1.2의 경로 지도·출도착점 비식별은 추가 작업이다. 실시간 워치 심박 스트리밍은 v1.2 제외 사항이다.

### 4.5 메이트 모집·문의 채팅·참가 신청

모집글, 문의 채팅, 참가 신청과 인앱 메이트 알림의 서버 계약은 구현됐다. 상세 API는 [P1 메이트 API 명세](./p1-mate-api-명세.md)를 기준으로 한다. 같이 운동 세션 진입, 모임 완료와 상대 평가는 후속 P1 범위다.

- 목록은 cursor/size를 사용하며 `nextCursor`, `hasNext`를 따라 추가 페이지를 요청한다.
- 상세의 `allowedActions`를 기준으로 신청·문의·수정·마감·취소 버튼을 노출한다. 클라이언트가 모집 상태만으로 권한을 추정하지 않는다.
- 문의 채팅은 범용 DM이 아니다. 문의와 신청은 독립적이고, 거절·취소·철회·모집 취소 뒤에는 `READ_ONLY` 상태로 기록만 조회한다.
- 메시지 전송에는 클라이언트가 생성한 UUID `clientMessageId`를 유지해 재시도한다. 동일 ID와 다른 본문인 경우 충돌 오류를 표시한다.
- 알림 목록의 `target`으로 모집글·방·메시지·신청 화면으로 이동하고, target 접근 권한 오류는 해당 화면을 열지 않는다.

- 작성 입력: 제목, sportCode 또는 커스텀 종목, 지역 ID, 날짜/시작 시각, 소요 시간(초), 정원, 난이도, 설명, 초보 환영, 공개 장소, 확정자 집결 위치, 1인 예상 비용(KRW), 공개 범위, 종목별 조건.
- 목록/상세 응답: postId, 작성자 userId/닉네임/사진, 공개 데이터, 참가 인원, 모집 상태, 내 신청 상태, version, 허용 행동, 접근 가능한 참가자·집결 위치.
- 종목별 조건: 현재 `mateFields()`는 6종목의 한국어 key/value Map. 서버는 고정 fieldCode·타입·허용값·복수 선택 여부·schemaVersion을 정의해야 한다. 명세의 전체 종목/사용자 추가 운동을 현재 6종목 구현과 구분한다.
- 평가: 대상 userId, 모임 ID, 평가 항목별 점수와 비공개 메모. 점수 배열의 위치 대신 고정 항목 코드를 합의한다.
- 모집 상태와 신청 상태는 독립 enum으로 관리한다. 정원 초과/중복 신청/마감 후 변경은 서버에서 원자적으로 검사한다.
- 개인 운동 종료와 모임 완료는 별도 행동이어야 한다. 현재 `MateFeatureState.completeWorkout()`은 개인 종료 시 모임 completed를 설정하므로 연동 시 수정이 필요하다.
- 참가 확정 후 DM 시작과 비공개 계정 DM 정책이 충돌하는 경우의 예외 여부를 결정해야 한다. 자동 예외를 가정하지 않는다.

### 4.6 커뮤니티·프로필 탐색·팔로우

신규 계약 필요: 공개/팔로잉 피드, 게시물 CRUD, 좋아요 추가/취소, 댓글 조회/작성/삭제, 사용자 프로필, 팔로워/팔로잉 목록, 팔로우 요청·수락·거절·취소·해제·팔로워 삭제.

- 게시물 입력: 본문, mediaIds, 첨부할 개인 운동 기록 ID와 공유 요약 범위, 공개 범위.
- 응답: postId, author.userId/닉네임/이미지, 본문·이미지 URL, 안전한 운동 요약, createdAt/updatedAt, 좋아요·댓글 수, likedByMe, 접근/수정/삭제 가능 여부, cursor.
- 관계 응답: 상대 계정 공개 여부, 내가 팔로우하는 상태, 상대가 나를 팔로우하는 상태, 요청 상태, 차단 여부, DM 허용 상태. 이름 대신 userId로 저장한다.
- 공개 게시물은 작성자 계정이 비공개여도 공개된다. 비공개 게시물은 작성자와 맞팔인 사용자에게만 노출한다. 관계 해제/차단 직후 목록·상세·첨부 접근에도 적용한다.
- 프로필 운동 기록 공유 범위와 첨부 요약의 필드를 명시하고 심박·칼로리 등 개인 상세값을 자동 공개하지 않는다.

### 4.8 공통 이미지·인바디

공통 업로드는 프로필/피드/DM/인바디 용도를 구분한다. 기기 `content://` URI는 서버나 상대 기기에서 열 수 없다. 업로드 생성·완료·실패·삭제, 최대 크기/형식/개수, mediaId·표시 URL·만료 시각을 합의한다. multipart와 업로드 URL 방식 중 하나를 확정하며 인바디 원본은 비공개로 취급한다.

- OCR: mediaId로 판독 요청 → jobId → UPLOADED/PROCESSING/COMPLETED/REVIEW_REQUIRED/FAILED 조회 → 판독값·필드별 신뢰도·오류 → 사용자 검수 후 기록 저장. 판독 완료와 사용자 저장 완료를 분리한다.
- 수동 기록 필수값(현재 UI): 측정일, 체중 kg, 골격근량 kg, 체지방률 %. recordId, 입력 출처, 수정 시각 필요.
- 추가값(현재 UI): 키 cm, 체지방량·제지방량 kg, BMI, 체수분 L, 단백질·무기질 kg, 복부지방률, 내장지방레벨, BMR kcal, 점수, 부위별 근육·지방 kg, 비만도 %, 권장 체중 kg.
- 누락값을 0으로 채우지 않는다. 추가값은 현재 한국어 Map이므로 고정 fieldCode와 단위로 매핑한다. v1.2의 체중조절량과 측정일시는 현재 UI와 차이가 있어 추가/표현 기준을 합의한다.
- 조회/수정/삭제와 날짜별 변화 기록 필요. 현재 UI 검증 범위는 미래일 불가, 체중 1~500kg, 골격근량 0~체중, 체지방률 0~100%. 이는 현재 구현 값이며 최종 서버 제약은 합의한다.
- 원본 보관/삭제 시점, 재분석 가능 기간, 건강정보 동의 철회 후 처리와 기록 삭제 결과를 정의한다. 예시 OCR 값은 실제 저장 데이터로 자동 이관하지 않는다.

### 4.9 관리자·광고와 기기 전용 기능

v1.2의 관리자·광고 기능은 제품 범위에 남아 있다. 관리자 권한·제재·신고 처리, 광고 노출 위치·기간·광고 표시·클릭/노출 수집·타겟팅 동의는 별도 상세 계약이 필요하다. 현재 모바일에서 필요한 운영 결과(계정 정지, 신고 결과, 공지/광고 카드)를 먼저 구분한다. 인바디를 광고 타겟팅에 사용하지 않는다.

테마, 애니메이션, 입력 포커스, 촬영 UI, 휴식 타이머 tick에는 전용 서버 API가 필요하지 않다. 계정 간 동기화가 필요한 설정만 서버 계약에 포함한다. 단체 채팅과 기기 직접 Bluetooth 통신은 v1.2 제외 범위다.

## 7. 연동 완료의 기준

각 기능은 화면에서 요청 → 서버 DB 반영 → 재조회 → 앱 재실행 후 일치까지 확인한다. Mock 화면 동작, Entity 존재, 문서 작성, 하위 브랜치 merge만으로 완료 처리하지 않는다.

대표 검증 흐름은 가입/로그인·프로필 재조회, 루틴→세션→세트 수정/삭제→완료 리포트, 서로 다른 두 계정의 메이트/DM/공개 범위, 이미지 업로드→OCR 실패/검수→인바디 저장, Samsung 지연 로그 후 리포트 갱신이다. 오류·권한 거절·중복 요청·충돌도 해당 기능과 함께 확인한다.

검토에 사용한 주요 코드: `AuthController/AuthDtos/AuthService`, `ProfileController/ProfileDtos/ProfileService`, `FitnessQueryController`, Android의 `FitMateModels`, `FrontendLocalStore`, `WorkoutSession`, `RunningFlow`, `MateFeatures`, `SocialFeatures/SocialSnapshot/CommunityAccounts`, `InbodyFlow`, `SamsungWorkoutUiModel`.
