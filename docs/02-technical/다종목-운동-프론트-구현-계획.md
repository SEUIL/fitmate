- 작성일: 2026-09-14
- 최종 수정일: 2026-09-14
- 버전: v1.0
- 상태: 확정
- 대상: Android Compose
- 구현 상태: 계획만 작성. 화면·상태·API 코드 구현 전

## 1. 목표와 연결 문서

개인 운동 선택에서 배드민턴·클라이밍·등산·골프를 시작하고, 공통 타이머와 종목별 입력을 거쳐 서버에 저장·재조회한다. 승인 근거는 [결정·회의 로그](../00-project/결정-회의-로그.md)의 `2026-09-14 다종목 개인 운동 시연 범위 확정`이다.

- [백엔드 계획](./다종목-운동-백엔드-구현-계획.md): API 필드·검증값의 단일 기준.
- [DB 계획](./다종목-운동-db-구현-계획.md): 공통 세션과 상세 저장 구조.
- [시연 계획](../03-qa/다종목-운동-시연-계획.md): 기능 확인과 발표 흐름.

## 2. 기존 코드 적용 지점

| 위치 | 적용 내용 |
|---|---|
| `data/model/FitMateModels.kt`의 `Sport` | 기존 여섯 종목 enum 재사용 |
| `ui/FitMatePrototypeApp.kt` | 개인 운동 진입 분기, 진행 중 기록 복귀, 저장 완료 후 목록 갱신 |
| `ui/RunningFlow.kt` | 타이머·결과 입력 흐름 참고. 러닝 GPS 로직은 복제하지 않음 |
| `ui/FrontendLocalStore.kt` | 기존 보관 패턴을 확인해 신규 초안 상태 추가 |
| `ui/ServerRecordApi.kt` | 신규 기록 POST/GET, 공통 목록 sportCode 필터 연결 |
| `ui/ServerRecords.kt` | 서버 기록 종목 필터·카드·상세 분기 확장 |
| `ui/WorkoutRecordBrowser.kt` | 로컬/예시 기록 화면과 진입 경로 확인, 신규 서버 기록과 출처 혼동 방지 |

위 경로는 `android/app/src/main/java/com/fitmate/app/` 기준이다. 신규 화면은 `ui/SportRecordFlow.kt`, 상태는 `ui/SportRecordState.kt`로 분리하는 것을 기본으로 한다. 추가 전 같은 이름의 파일을 확인한다.

## 3. 사용자 흐름

`개인 운동 선택 → 종목/유형 선택 → 시작 → 일시정지·재개 → 종료 → 결과 확인/입력 → 저장 → 리포트 → 기록에서 재조회`

| 화면 | 필수 동작 |
|---|---|
| 종목 선택 | 헬스·러닝·배드민턴·클라이밍·등산·골프. 활성 서버 종목과 현재 구현 지원 목록의 교집합 사용 |
| 준비 | 선택 종목명, 유형 선택, 선택 장소 입력, 시작 버튼 |
| 진행 | 종목·유형·실제 운동 시간, 일시정지/재개, 종료 |
| 종료 입력 | 날짜·시간 요약, 종목별 결과·메모, 저장 전 수정, 저장 버튼 |
| 결과 | 서버 저장 확인, 시간·입력한 결과 표시, 기록 목록 이동 |
| 기록 목록/상세 | 전체와 여섯 종목 필터, 최신 기존 목록 순서, 상세 재조회 |

공통 타이머 화면 하나와 종목별 입력 블록을 사용한다. 타이머 진행 중 유형은 고정하고, 종료 입력 단계에서 바꾸면 새 유형에 맞지 않는 결과 필드를 비운다. 신규 종목에 헬스 루틴·세트·중량 입력을 표시하지 않는다.

기존 메이트 운동 시작 진입은 확장하지 않는다. `/sports` 활성화로 기존 가입·프로필·모집 선택에 종목이 보이는 것은 유지하되 신규 운동 세션 연결을 만들지 않는다.

## 4. 종목별 입력 UI

| 종목 | 유형 라벨 | 결과 입력 |
|---|---|---|
| 배드민턴 | 단식 / 복식 / 연습 | 게임 수, 승리 수 |
| 클라이밍 | 볼더링 / 리드 / 탑로프 | 시도 수, 완등 수, 난이도 메모 |
| 등산 | 등산 / 트레킹 | 산·코스명, 거리(km) |
| 골프 | 연습 / 스크린 / 필드 | 연습: 타격 수. 스크린·필드: 진행 홀 수, 총 타수 |

종목·유형·시간 외 결과 필드는 모두 선택이다. 미입력은 null로 보내고 `0`으로 자동 채우지 않는다. 상세에는 미입력 항목을 숨기거나 `미입력`으로 표시한다.

- 공통 선택 항목: 장소 최대 100자, 메모 최대 500자.
- 난이도·코스명 최대 100자. 난이도 사전이나 코스 검색은 만들지 않는다.
- 숫자 필드의 범위와 의존 조건은 백엔드 계획과 동일하게 적용한다. 승리/완등 수만 입력하면 전체 횟수 입력을 안내한다.
- 등산 거리는 소수점 셋째 자리까지 km로 입력하고 decimal 방식으로 정수 m로 변환한다. 음수·범위 초과·변환 실패를 입력란에서 안내한다.
- 골프 라운드는 부분 진행을 위해 1~18홀 입력을 허용한다. 타수를 입력하면 진행 홀 수도 입력한다.
- 날짜는 서버 UTC 시각을 기기 시간대로 표시한다. 실제 운동 시간은 일시정지를 제외하며 총 경과 시간과 구분한다.

## 5. 타이머와 임시 보관

초안은 사용자 ID 기준으로 분리하며 종목·유형·시작 시각·누적 운동 시간·현재 상태·종료 시각·결과 입력값·`clientRecordId`를 보관한다. 계정 전환 시 다른 사용자의 초안을 표시하거나 전송하지 않는다.

| 상태 | 동작 |
|---|---|
| 준비 | 시작 시 한 번만 UUID 생성 |
| 운동 중 | monotonic clock 기준으로 시간 계산, 화면 tick 횟수를 누적 시간으로 사용하지 않음 |
| 일시정지 | 누적 시간을 확정하고 쉬는 시간은 활동 시간에서 제외 |
| 종료 입력 | 종료 시각과 활동 시간을 고정, 결과 입력값 임시 보관 |
| 저장 중 | 전송 본문과 ID를 고정, 중복 누름 차단 |
| 저장 확인 | 서버 응답 확인 후 해당 초안 제거, 결과 화면 전환 |

화면 회전·화면 이동 후에도 시간을 유지한다. 동일 기기 부팅 세션에서 앱이 재생성되면 보관된 monotonic 기준으로 복원한다. 기기 재부팅 등으로 기준이 유효하지 않으면 마지막 보관 시간에서 일시정지 상태로 복원하고 안내한다. 백그라운드 서비스·자동 동기화 큐는 신규 도입하지 않는다.

저장은 상태 전환과 입력 변경 시 수행하고, 진행 시간 체크포인트는 약 10초 간격으로 보관한다. 비정상 종료·재부팅에서는 마지막 체크포인트 이후 일부 시간이 복구되지 않을 수 있음을 구현 검증에 포함한다. 일반적인 화면 꺼짐은 지속되는 monotonic 기준으로 계산한다.

진행 중 신규 기록은 하나로 제한하고 다른 운동 진입 시 기존 기록으로 돌아가거나 초안을 취소하도록 안내한다. 기존 헬스·러닝 진행 상태와도 충돌하지 않게 진입 지점에서 확인한다. 취소는 기기 초안만 제거하며 서버 기록은 만들지 않는다.

## 6. 저장 오류와 복구

- 저장 전 오류는 필드 아래 표시하고 입력을 유지한다.
- 저장 시작 시 정확한 요청 본문과 ID를 함께 보관한다. 응답을 받기 전까지 입력을 잠그고 재전송해도 같은 본문·ID를 사용한다.
- 400처럼 저장 실패가 확실하면 입력 편집을 다시 허용한다.
- 네트워크 단절·응답 유실·서버 오류로 저장 여부가 불명확하면 `GET /sport-records/{id}`로 확인한다. 저장된 내용이 같으면 성공으로 복구한다.
- GET 실패 시 초안을 유지한다. 조회가 404여도 즉시 새 ID로 저장하지 않고 원래 요청을 동일 ID로 재시도하여 늦게 끝난 요청과 중복되지 않게 한다.
- 동일 ID의 내용 충돌 409는 기존 기록 재조회와 안내로 처리하고 자동 덮어쓰기는 하지 않는다.
- 401은 기존 토큰 갱신/재로그인 흐름을 사용하되 로그인 사용자가 초안 소유자와 같은지 확인한다.

저장하지 못한 화면을 완료로 표시하지 않는다. 오프라인에서도 초안을 보관할 수 있지만 서버 저장·재조회 완료에는 연결이 필요하다.

## 7. 기록 목록 연결

현재 `ServerRecords.kt`는 헬스/러닝 두 분기이며, `ServerRecordDetail`도 running boolean을 사용한다. 신규 경로는 종목 코드로 분기하여 헬스 → 기존 report, 러닝 → 기존 running GET, 신규 네 종목 → sport-records GET을 선택한다.

- 전체·종목 필터는 가로 스크롤 칩으로 배치한다. 여섯 종목을 동일 행에 강제로 압축하지 않는다.
- 공통 `/workout-sessions?status=COMPLETED` 목록과 서버 sportCode 필터를 사용해 전체/개별 목록을 구성한다. 종목 변경 시 페이지와 선택 상세를 초기화한다.
- 기존 목록의 새로고침·더 보기·ID 중복 제거·로딩·빈 상태·오류 재시도를 유지한다.
- 공통 목록의 신규 종목 카드는 종목·날짜·유형 상세 진입을 중심으로 표시한다. 세트/볼륨을 표시하지 않는다.
- 신규 상세에는 장소·시간·입력 결과·메모만 표시하고 외부 운동 연결 영역을 붙이지 않는다.
- 프로필 운동 개수는 공통 완료 세션 목록 기준으로 한 번만 센다. 신규 전용 목록 개수를 다시 더하지 않는다. 저장 후 현재 사용자 기록과 개수를 갱신한다.
- 기존 로컬 예시 보기는 서버 저장 성공으로 표현하지 않는다. 신규 시연 기록은 실제 API를 통해 준비한다.

## 8. 구현 순서와 한정 검증

| 순서 | 구현 단위 | 완료 판단 |
|---|---|---|
| 1 | 상태·공통 타이머·유형 UI | 네 종목 시작/정지/재개/종료 가능 |
| 2 | 결과 입력·검증·초안 보관 | 선택 결과 없이도 유효 기록 생성, 재진입 복원 |
| 3 | 저장·실패 복구 | 서버 저장 성공과 재시도 중복 방지 |
| 4 | 목록·상세·개수 연결 | 저장 결과를 재진입 후 조회, 종목 분기 정상 |
| 5 | 표시 확인 | 라이트/다크, 숫자 키보드, 긴 텍스트에서 조작 가능 |

후속 구현 검증은 시간 누적·일시정지·복원, 거리 변환, 조건부 필드 제거, 요청 ID 재사용과 해당 화면의 저장·재조회 흐름에 한정한다. 헬스·러닝은 바뀐 목록·진입 경로만 최소 확인한다. 이번 문서 작성에서는 테스트·빌드·앱을 실행하지 않았고 전체 테스트는 실행하지 않는다.
