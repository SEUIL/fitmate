# [검토 중] 인바디·프로필 기반 운동 추천 확장 API

- 작성일: 2026-09-14 / 최종 수정일: 2026-09-15
- 버전: v1.3
- 상태: 검토 중
- 범위: 1번 맞춤 운동 추천. 운동 후 AI 종합 리포트는 제외한다.
- 기존 기반: PR #56. 기존 `POST /api/v1/workout-recommendations` 응답 구조는 유지한다.

## 1. 처리 경계

프로필·본인 인바디·활성 헬스 카탈로그를 짧은 읽기 트랜잭션에서 DTO로 분리한다. 추천 생성 요청을 별도 트랜잭션으로 접수한 뒤, 기존 Spring Boot 내부의 제한된 실행기(작업 2개, 대기 8개)에서 AI를 호출한다. 외부 요청 중 DB 트랜잭션을 유지하지 않는다.

AI는 허용된 카탈로그의 운동 ID·날짜·세트·반복·휴식만 제안한다. 운동 이름, 안내 문구, 추천 근거, 예상 시간은 서버가 생성한다. 임의의 텍스트·중량·추가 필드는 수용하지 않는다. AI가 없거나 실패·형식 오류·제약 위반이면 동일 검증기를 통과한 기본 추천으로 대체한다. 기본 추천도 실패하면 `FAILED`와 조건 수정 안내를 반환한다.

## 2. API

모든 경로는 `/api/v1/workout-recommendations/plans` 기준이며 인증이 필요하다. 성공은 기존 `data` envelope, 실패는 기존 `error` envelope를 사용한다. 생성 접수는 200이며 `status`로 완료 여부를 구분한다.

| 메서드 / 경로 | 계약 |
|---|---|
| GET `/options` | 서버의 목표·숙련도, 추천 지원 운동, AI 사용 가능 여부, 동의 버전·개발용 안내 |
| POST `/` | 조건과 `requestId`를 접수. 초안 ID는 `requestId`와 같다. |
| GET `/{id}` | 본인 초안의 상태·버전·결과·저장 루틴 ID 조회 |
| POST `/{id}/cancel` | 저장 전 초안 취소. 진행 중 외부 요청의 전송 자체를 되돌리지는 못하며, 늦은 결과 반영은 차단한다. |
| GET `/{id}/alternatives?day=1&exerciseId=...` | 같은 부위, 허용 기구·제외 조건·전체 시간 검증을 만족하는 대체 후보와 예상 시간 차이 |
| POST `/{id}/replace` | `version`, `day`, `exerciseId`, `replacementId`. 세트·반복·휴식 유지 후 전체 재검증 |
| POST `/{id}/save` | `version` 필수. 새 루틴과 추천 근거를 한 트랜잭션으로 저장. 같은 초안 재저장은 같은 루틴 반환 |

생성 입력:

```json
{
  "requestId": "00000000-0000-4000-8000-000000000001",
  "daysPerWeek": 2,
  "sessionMinutes": 30,
  "equipmentTypes": ["MACHINE", "CABLE"],
  "preferredExerciseIds": [],
  "excludedExerciseIds": [],
  "externalAiConsent": false
}
```

`inbodyRecordId`는 선택 입력이며 본인 기록만 허용한다. 미지정 시 최신 기록을 자동으로 사용하지 않는다. `equipmentTypes`가 비면 전체 기구, 지정하면 해당 기구와 맨몸을 허용한다. 맨몸만 가능하면 `BODYWEIGHT` 하나를 보낸다. 선호·제외 ID는 각각 최대 100개이고 중복 지정·비활성 ID·기구와 모순된 선호는 거절한다. 선호는 가능하면 반영하는 조건이며 제외는 반드시 지켜야 한다.

동의한 요청은 `externalAiConsent: true`, `consentVersion: "workout-plan-demo-v1"`을 함께 보낸다. 서버는 버전과 활성화 설정도 확인한다. 계정·이메일·연락처·지역·나이·성별·키·인바디 원본 이미지는 AI 입력에 없다. 선택 인바디에서는 체지방률·골격근량만 외부 입력에 사용한다. 기본 추천은 체성분으로 운동이나 중량을 변경하지 않는다.

응답은 `id`, `status`, `version`, nullable `result`, nullable `routineId`, nullable `message`다. `result`에는 이름, `source: AI|RULE_BASED`, 목표·숙련도, 원래 조건, 선택 측정일, 근거·정보 부족 안내, 날짜별 운동·세트·반복·휴식·예상 시간이 포함된다.

## 3. 서버 제약과 시간 의미

아래 값은 프론트 시안의 예시를 복사한 고정 구성값이 아니라, 이번 반복형 헬스 추천 검증기의 보수적인 허용 범위다. 별도 운동 전문성 검수를 완료한 정책을 의미하지 않는다.

- 횟수: 1~7일, 가용 시간: 20~180분. 입력 일수만큼 독립적으로 구성하고 단순 분할 병합을 하지 않는다.
- 날짜별 운동 2~6개, 동일 날짜의 운동 ID 중복 금지. 각 운동 반복 6~15회, 휴식 45~150초. 분할의 하체·당기기 일차를 위해 일별 최소 종목 수를 조정했다.
- 입문·6개월 미만은 운동당 1~3세트·일일 최대 12세트, 이후는 1~4세트·일일 최대 20세트.
- 하루 최소 그룹 수를 강제하지 않는다. 주간 전체에는 PUSH/PULL/LEGS가 모두 있어야 하며 CORE로 주요 그룹을 대신할 수 없다. 주요 그룹의 주간 최대 세트 수는 최소의 3배 이내다. 한 그룹에 하루 8세트를 초과하지 않고 날짜별 총 시간은 최장/최단 1.5배 이내다.
- 기본 추천은 입문·6개월 미만 또는 주 3일 이하에서 전신을 우선한다. 그 외에는 가용 종목이 충분하면 상체/하체 교대, 주 6일 이상이며 각 주요 그룹에 2종목 이상이면 밀기/당기기/하체 순환을 우선한다. 짧은 시간·제한된 카탈로그로 분할을 검증할 수 없으면 검증된 전신 대안을 시도하고, 이것도 불가능하면 조건 수정 안내를 반환한다. AI에는 권장 일차별 그룹을 전달하되 다른 구성이어도 전체 검증을 통과하면 수용한다.
- 준비운동 300초. 운동 항목 시간은 `세트 × 반복 × 4초 + (세트−1) × 휴식초 + 운동 전환·준비 60초`다.
- 체지방 감소 목표의 기본 유산소는 `min(600초, 회당 가용 초/6)`이다. 나머지 목표는 기본 유산소 0초다.
- 총 예상 시간 = 준비운동 + 전체 항목 + 유산소. 모든 날짜가 입력한 가용 시간 이하여야 한다. 정확히 그 시간을 채우려고 운동량이나 휴식을 임의로 늘리지 않으며, 실제 예상 시간과 남는 시간의 의미를 안내한다.
- 기존 루틴·운동 세션 API가 반복 횟수 중심이어서 V2의 시간 유지형 플랭크는 지원 후보에서 제외한다. 향후 시간형 운동 지원 시 카탈로그의 목표 단위와 기록 계약을 함께 확장해야 한다.
- 중량·질환·교정 운동은 제안하지 않는다. 기본 추천은 초보자에게 머신·케이블을 우선하고, 정보 부족·측정일·현재 상태와의 차이를 안내한다.

## 4. 상태·동시성·재시도

`GENERATING → READY → SAVED`, 또는 `GENERATING → FAILED`, 저장 전 `CANCELED`를 사용한다.

- 같은 `requestId`·같은 조건은 같은 초안을 반환한다. 다른 조건 재사용은 409 `IDEMPOTENCY_KEY_CONFLICT`다. 조건 변경·취소 후 새 생성에는 새 ID를 쓴다.
- 생성 ID 고유키와 짧은 행 잠금으로 중복 AI 작업을 막는다. 다른 사용자의 ID를 제출해도 그 사용자의 행을 덮어쓰지 않는다.
- AI 연결·읽기 제한은 각각 설정값(1~30초)이다. 접수 후 120초 이상 멈춘 요청은 조회·재시도 시 `FAILED`로 전환한다. 실패한 동일 요청은 재시도 가능하다.
- 생성 토큰으로 취소·재시도 뒤 이전 응답의 결과 반영을 차단한다. 대기 중 취소한 작업은 실행 전 상태 확인으로 전송을 건너뛴다.
- 교체는 본인 초안·버전·READY 상태를 확인하고 실패 시 기존 결과를 보존한다. 같은 운동 부위의 후보로 제한하고 저장 시 활성 카탈로그·본인 인바디를 다시 확인한다.
- 저장은 초안 행 잠금 아래 루틴·항목·메타데이터·초안 상태를 함께 확정한다. 응답 유실 후 재저장은 기존 루틴을 반환한다. 사용자가 루틴을 삭제한 경우 재저장으로 몰래 복구하지 않는다.
- 프로세스 재시작 후 백그라운드 작업을 자동 복구하는 별도 작업 큐는 없다. 120초 만료 후 같은 요청 재시도를 사용한다.

## 5. 저장·조회·운동 시작

V1~V22는 수정하지 않았다. V23은 `fitness_workout_plans`를 추가하고 기존 `fitness_routines`에 nullable `recommendation_json`을 추가한다. 신규 테이블은 본인 소유자, 요청·정규화된 검증 결과, 상태·버전·작업 토큰·시각·저장 루틴 ID만 보관한다. 인바디 수치·원본 이미지·AI 원문 응답은 추천 테이블에 보관하지 않는다.

저장한 추천은 기존 `MANUAL` 루틴 항목으로 변환하되 목표·숙련도·난이도와 원래 추천 근거·조건도 보존한다. `GET /api/v1/routines/{id}`의 추가 필드 `recommendation`에서 저장 당시 스냅샷을 조회한다. 이후 직접 편집한 루틴 구성과 저장 당시 추천이 다를 수 있음을 앱에서 구분한다. 운동 시작은 기존 루틴 선택·준비 화면·`POST /workout-sessions`를 재사용하며 기존 일차 순환 로직을 유지한다.

## 6. 동의 정책·활성화 상태

UI 적용 후 `GET /api/v1/routines/{id}`에 `nextSplitDayNo`를 추가했다. 본인 또는 공용 템플릿 접근 권한을 확인한 뒤, 해당 사용자의 완료 세션 수를 분할 수로 나눈 나머지 + 1을 반환한다. 운동 준비 화면은 이 응답의 해당 일차 종목만 표시한다. 조회는 세션을 생성하거나 다음 일차를 소비하지 않는다. 실제 세션 생성 시에는 기존 서버 순환 규칙을 다시 적용한다. 필드를 지원하지 않는 구버전 서버에서는 앱이 1일차를 추측해 시작하지 않고 재조회 안내를 표시한다. 추가 migration은 없다.

기존 `GET /api/v1/routines/recommended`도 같은 사용자별 계산을 적용해 추천 응답과 상세 조회의 다음 일차가 일치한다.

공개 서비스의 동의 문구·외부 전송·보관·삭제 정책은 미확정이다. 개발용 안내를 공개용 확정 정책으로 표시하지 않는다. 현재 기본 설정 `FITMATE_WORKOUT_PLAN_AI_ENABLED=false`는 외부 구성 생성을 차단한다. 개발 범위의 정책 확인과 연결 설정 후에만 테스트/개발 환경에서 활성화한다. 키·모델·접속 정보는 기존 서버 설정을 사용하고 키를 앱에 포함하지 않는다.

기존 설명 전용 API도 명시적인 현재 버전 동의와 같은 서버 활성화 설정 없이는 외부 AI를 호출하지 않고 `aiSummary: null`을 반환한다. 그 외 기존 응답 필드와 기본 추천 동작은 유지한다.

자동 보관기간·삭제 정책은 이번 작업 범위에서 제외했다. 승인된 기존 개발 DB에는 백업 후 V23·V24가 적용됐으며 로컬 실행에서만 AI를 활성화했다. 공개 서비스 활성화를 뜻하지 않는다. 검증 범위는 [추천 확장 검증 기록](../03-qa/운동-추천-확장-검증-260914.md)을 따른다.
