# 커스텀 관심 운동 프론트엔드 연동 가이드

- 작성일: 2026-09-06
- 최종 수정일: 2026-09-06
- 버전: v1.0
- 상태: 검토 중
- 대상: FitMate Android Client

## 1. 목적

프로필 화면의 `+ 직접 추가`로 입력한 관심 운동을 회원가입 및 프로필 API에 저장하고 다시 표시하기 위한 계약을 설명한다.

커스텀 관심 운동은 사용자 프로필에만 속한다. 서버가 관리하는 운동 종목과 숙련도는 `sports`, 사용자가 직접 입력한 이름은 `customSports`로 분리한다. 커스텀 운동을 등록해도 `GET /sports` 결과나 루틴 추천 대상은 바뀌지 않는다.

## 2. 연동 전 현재 Android 상태

현재 Android 앱은 `MockFitMateRepository`를 사용하고 `UserProfile.interests: Set<Sport>`에 enum 운동만 보관한다. 네트워크 API와 access token 저장소는 아직 연결되어 있지 않다.

프론트엔드 연동 시 다음 값이 추가로 필요하다.

- 서버 관리 관심 운동: `sports`
- 직접 입력 관심 운동: `customSports`
- 프로필 동시 수정 제어 값: `profile.version`
- 인증 요청용 access token

`UserProfile.interests`에 커스텀 이름을 억지로 넣지 않는다. enum 목록과 문자열 목록을 별도 상태로 관리해야 서버 계약과 일치한다.

## 3. 공통 계약

| 항목 | 값 |
|---|---|
| 로컬 서버 Base URL | `http://localhost:8080/api/v1` |
| Android Emulator Base URL | `http://10.0.2.2:8080/api/v1` |
| 요청 및 응답 | `application/json` |
| 인증 | `Authorization: Bearer {accessToken}` |
| 성공 응답 | `{ "data": ... }` |
| 실패 응답 | `{ "error": { "code", "message", "fields" } }` |

커스텀 관심 운동 DTO는 다음 한 필드만 사용한다.

```json
{
  "name": "필라테스"
}
```

검증 규칙은 다음과 같다.

- 사용자당 최대 20개
- 각 이름은 1~50자
- 빈 문자열, 공백뿐인 값, 제어 문자는 허용하지 않음
- 서버는 유니코드, 앞뒤 공백, 연속 공백과 대소문자를 정규화해 중복 검사
- `CrossFit`, ` crossfit `, `ＣｒｏｓｓＦｉｔ`은 같은 이름으로 판단
- 같은 사용자의 중복은 `400 VALIDATION_ERROR`
- 다른 사용자는 같은 이름을 각각 등록할 수 있음
- 응답은 정규화된 이름순이며 입력 순서를 보장하지 않음

클라이언트에서도 저장 버튼을 누르기 전에 빈 이름과 20개 초과를 막되, 서버 오류 응답도 반드시 처리한다.

## 4. 회원가입 연동

### 4.1 요청

`POST /api/v1/auth/signup`

```json
{
  "email": "user@example.com",
  "password": "test-password-123",
  "nickname": "fitmate",
  "sports": [
    {
      "sportCode": "HEALTH",
      "skillLevel": "BEGINNER"
    }
  ],
  "customSports": [
    { "name": "필라테스" },
    { "name": "크로스핏" }
  ],
  "goals": [
    {
      "goalCode": "HABIT",
      "primary": true
    }
  ],
  "consentDocumentIds": [
    "20000000-0000-0000-0000-000000000001",
    "20000000-0000-0000-0000-000000000002"
  ],
  "deviceId": "android-installation-id"
}
```

직접 추가한 운동이 없으면 `customSports: []`를 보내거나 필드를 생략한다. 기존 클라이언트를 위해 생략 시 빈 목록으로 처리한다. `sports`에는 P0 필수 종목인 `HEALTH`와 숙련도를 계속 보내야 한다.

### 4.2 응답

성공 상태는 `201 Created`다.

```json
{
  "data": {
    "user": {
      "id": "ea1155ab-4a65-46fb-953d-974d33e3ced9",
      "email": "user@example.com",
      "accountStatus": "ACTIVE",
      "profile": {
        "nickname": "fitmate",
        "displayName": "fitmate",
        "visibility": "PUBLIC",
        "weightUnit": "KG",
        "timezoneId": "Asia/Seoul",
        "version": 0
      },
      "customSports": [
        { "name": "크로스핏" },
        { "name": "필라테스" }
      ]
    },
    "tokens": {
      "accessToken": "access-token",
      "accessTokenExpiresInSeconds": 900,
      "refreshToken": "refresh-token"
    }
  }
}
```

회원가입 성공 후 access token과 refresh token을 인증 저장소에 보관한다. 프로필 화면에 들어갈 때는 회원가입 응답에만 의존하지 않고 내 프로필을 다시 조회한다.

## 5. 프로필 조회 연동

`GET /api/v1/users/me`

```http
Authorization: Bearer {accessToken}
```

관심 운동과 관련된 응답 형태는 다음과 같다.

```json
{
  "data": {
    "profile": {
      "nickname": "fitmate",
      "displayName": "홍길동",
      "visibility": "PUBLIC",
      "weightUnit": "KG",
      "timezoneId": "Asia/Seoul",
      "version": 0
    },
    "sports": [
      {
        "sportCode": "HEALTH",
        "skillLevel": "BEGINNER"
      }
    ],
    "customSports": [
      { "name": "크로스핏" },
      { "name": "필라테스" }
    ]
  }
}
```

화면 진입 시 `data.profile.version`을 편집 상태에 함께 저장한다. `sports`는 서버 관리 선택 칩으로, `customSports`는 직접 추가한 칩으로 표시한다.

## 6. 프로필 수정 연동

`PATCH /api/v1/users/me/profile`

```http
Authorization: Bearer {accessToken}
Content-Type: application/json
```

프로필 수정 API는 커스텀 운동 전용 API가 아니다. 닉네임, 공개 범위, 지역, 시설, 가능 시간, 운영 운동, 커스텀 운동과 목표를 함께 수정할 수 있는 부분 수정 API다. `version`은 모든 수정 요청에 필수다.

커스텀 운동만 교체하는 요청은 다음과 같다.

```json
{
  "version": 0,
  "customSports": [
    { "name": "수영" },
    { "name": "클라이밍" }
  ]
}
```

성공 상태는 `200 OK`다. 응답은 `GET /users/me`와 같은 전체 내 프로필 구조이며 `data.profile.version`이 1 증가한다. 로컬 상태를 요청값으로 추측해 갱신하지 말고 성공 응답 전체를 새 화면 상태로 사용한다.

### 6.1 필드 전달 방식

| 요청 형태 | 동작 |
|---|---|
| `customSports` 생략 | 기존 목록 유지 |
| `customSports: null` | 기존 목록 유지. 클라이언트에서는 생략 방식 권장 |
| `customSports: [...]` | 전달한 목록으로 전체 교체 |
| `customSports: []` | 커스텀 관심 운동 전체 삭제 |

항목 하나를 삭제할 때도 별도 DELETE API를 호출하지 않는다. 삭제할 항목을 제외한 전체 목록을 PATCH 요청으로 보낸다.

예를 들어 `[필라테스, 크로스핏]`에서 필라테스를 지우려면 다음처럼 보낸다.

```json
{
  "version": 1,
  "customSports": [
    { "name": "크로스핏" }
  ]
}
```

기존 운영 운동 숙련도와 함께 수정할 수도 있다.

```json
{
  "version": 2,
  "sports": [
    {
      "sportCode": "HEALTH",
      "skillLevel": "UNDER_6_MONTHS"
    }
  ],
  "customSports": [
    { "name": "필라테스" }
  ]
}
```

`customSports`가 있어도 `sports`의 필수 `HEALTH` 숙련도를 대신할 수 없다.

## 7. version 충돌 처리

두 기기나 두 화면이 같은 version으로 수정하면 먼저 처리된 요청만 성공한다. 나중 요청은 다음 오류를 받는다.

```json
{
  "error": {
    "code": "VERSION_CONFLICT",
    "message": "수정 버전이 일치하지 않습니다.",
    "fields": []
  }
}
```

프론트엔드는 `409 VERSION_CONFLICT`를 받으면 다음 순서로 처리한다.

1. `GET /users/me`를 다시 호출한다.
2. 서버의 최신 프로필과 `version`을 화면에 반영한다.
3. 사용자에게 다른 곳에서 프로필이 변경되었다고 알린다.
4. 사용자가 변경 내용을 확인하고 다시 저장하게 한다.

최신 데이터를 확인하지 않은 자동 재시도는 다른 기기의 변경을 덮어쓸 수 있으므로 사용하지 않는다.

## 8. Android DTO 예시

프로젝트에는 Gson이 포함되어 있으므로 DTO는 다음 형태로 시작할 수 있다. 실제 네트워크 라이브러리에 맞춰 함수 선언만 조정한다.

```kotlin
data class ApiResponse<T>(
    val data: T,
)

data class ApiErrorResponse(
    val error: ApiError,
)

data class ApiError(
    val code: String,
    val message: String,
    val fields: List<ApiErrorField> = emptyList(),
)

data class ApiErrorField(
    val field: String,
    val reason: String,
)

data class CustomSportDto(
    val name: String,
)

data class UpdateProfileRequest(
    val version: Long,
    val nickname: String? = null,
    val visibility: String? = null,
    val sports: List<SportSelectionDto>? = null,
    val customSports: List<CustomSportDto>? = null,
)

data class SportSelectionDto(
    val sportCode: String,
    val skillLevel: String,
)

data class MyProfileResponse(
    val profile: ProfileDto,
    val sports: List<SportSelectionDto>,
    val customSports: List<CustomSportDto>,
)

data class ProfileDto(
    val nickname: String,
    val visibility: String,
    val version: Long,
)
```

부분 수정 DTO를 직렬화할 때 `null` 필드는 JSON에서 제외하도록 설정한다. 빈 목록은 삭제 의미가 있으므로 빈 목록까지 제외하는 직렬화 설정은 사용하지 않는다.

## 9. 화면 상태와 저장 흐름

프로필 화면은 다음 상태를 구분한다.

| 상태 | 화면 동작 |
|---|---|
| 조회 중 | 편집 버튼 비활성화 또는 로딩 표시 |
| 조회 성공 | 운영 운동과 커스텀 운동 칩 표시, version 보관 |
| 직접 추가 | 앞뒤 공백을 제거한 이름을 임시 목록에 추가 |
| 저장 중 | 중복 요청 방지를 위해 저장 버튼 비활성화 |
| 저장 성공 | 응답 전체와 새 version으로 화면 상태 교체 |
| `400 VALIDATION_ERROR` | 서버 message를 입력 영역에 표시 |
| `401` | token 갱신 후 한 번 재요청하거나 로그인 화면 이동 |
| `409 VERSION_CONFLICT` | 최신 프로필 재조회 후 충돌 안내 |
| 네트워크 오류 | 편집값을 유지하고 재시도 제공 |

취소 버튼은 서버 요청 없이 편집 전 서버 응답 상태로 복원한다. 저장 성공 전에는 화면의 영구 프로필 상태를 바꾸지 않는다.

## 10. 현재 UI에서 필요한 변경 지점

- `UserProfile`에 `customSports: List<String>`과 `version: Long` 추가
- `ProfileScreen`에 직접 추가 입력창, 추가 버튼과 삭제 가능한 커스텀 칩 추가
- `MockFitMateRepository` 대신 인증된 프로필 조회·수정 repository 연결
- 화면 진입 시 `GET /users/me` 호출
- 저장 시 변경된 필드와 최신 version으로 `PATCH /users/me/profile` 호출
- 성공 응답을 화면 상태에 반영
- `VALIDATION_ERROR`, 인증 만료, `VERSION_CONFLICT`, 네트워크 오류 표시

회원가입 화면에서도 같은 `CustomSportDto`를 재사용해 `POST /auth/signup`의 `customSports`에 포함한다.

## 11. 완료 확인 항목

- 회원가입에서 커스텀 운동을 등록하고 프로필 재조회 후 동일한 이름이 보인다.
- 프로필 수정에서 커스텀 운동을 추가, 이름 변경 및 삭제할 수 있다.
- `customSports`를 생략한 다른 프로필 수정에서 기존 목록이 유지된다.
- 빈 배열을 보내면 커스텀 운동만 삭제되고 `sports`의 `HEALTH`는 유지된다.
- 정규화 후 중복 이름과 20개 초과 입력에서 오류를 표시한다.
- 서로 다른 사용자에게 같은 커스텀 운동 이름을 등록해도 데이터가 섞이지 않는다.
- version 충돌 시 최신 프로필을 다시 조회하고 사용자 변경을 자동으로 덮어쓰지 않는다.
- `GET /sports` 결과에 커스텀 운동이 포함되지 않는다.
