# 다종목 운동 백엔드 구현 계획

- 작성일: 2026-09-14
- 최종 수정일: 2026-09-14
- 버전: v1.1
- 상태: 확정
- 대상: Kotlin Spring Boot Backend
- 구현 상태: 계획만 작성. 코드 변경 및 실행 검증 전

## 1. 목적과 범위

배드민턴·클라이밍·등산·골프를 개인 운동으로 기록한다. 기기의 공통 타이머로 운동하고 종료 후 결과를 입력하여 서버에 저장한 뒤 다시 조회하는 것이 완료 기준이다.

사용자 승인과 후속 Action Item의 기준은 [결정·회의 로그](../00-project/결정-회의-로그.md)의 `2026-09-14 다종목 개인 운동 시연 범위 확정`이다. 이 문서의 API 이름과 세부 검증값은 승인된 범위를 구현하기 위한 설계 기준이며 이미 구현된 계약이 아니다.

- 포함: 신규 네 종목의 완료 기록 저장·목록·상세, 기존 기록 목록 연결, 소유자 검증, 중복 저장 방지.
- 제외: 신규 종목의 메이트 운동 시작, 저장 후 편집·삭제, 추천 루틴, 전문 분석·순위, GPS·지도·Samsung Health·Fit3 연결, 자동 칼로리 계산.
- 연계: [DB 계획](./다종목-운동-db-구현-계획.md), [프론트 계획](./다종목-운동-프론트-구현-계획.md), [시연 계획](../03-qa/다종목-운동-시연-계획.md).

v1.1은 같은 결정 로그의 `2026-09-14 백엔드·DB 검토 보완 확정`을 반영한다. 백엔드·DB 담당의 완료 기준은 API·migration의 한정 검증과 연동 계약 전달까지다. Android 구현·실기기 UI 검증·발표 시연은 별도 담당자가 수행하며 백엔드 완료를 기다리게 하는 조건으로 두지 않는다.

## 2. 현재 코드와 재사용 범위

| `backend/.../running/application/RunningRecordService.kt` | 완료 러닝과 공통 세션을 함께 저장 | 공통 세션 + 상세 기록의 트랜잭션 패턴 참고 |
| `backend/.../workout/api/WorkoutController.kt` | 공통 목록은 status·cursor·size 지원 | 선택적 sportCode 필터 추가 |

## 3. API 계약

공통 접두사는 `/api/v1`, 인증과 성공·오류 응답 포맷은 기존 API를 사용한다.

| Method | 경로 | 역할 |
|---|---|---|
| POST | `/sport-records` | 신규 네 종목 완료 기록 생성. 최초 성공 201, 동일 요청 재전송은 200 |
| GET | `/sport-records/{recordId}` | 본인 기록 상세 및 결과 리포트 |
| GET | `/sport-records?sportCode={code}&cursor=0&size=20` | 신규 네 종목 목록. sportCode 생략 시 네 종목 전체 |
| GET | `/workout-sessions?status=COMPLETED&sportCode={code}&cursor=0&size=20` | 기존 목록에 종목 필터 추가. sportCode 생략 시 모든 종목 |

`recordId`는 공통 세션 ID와 동일하다. 신규 기록은 완료 시 공통 세션을 `COMPLETED`로 생성하고 루틴·세트 행은 생성하지 않는다. 운동 진행·일시정지·취소는 기기 임시 상태로 처리한다.

공통 목록의 기존 응답 필드는 유지한다. 신규 종목은 `sportCode`, `startedAt`, `endedAt`로 카드 제목·날짜를 표시하고 상세 클릭 시 신규 GET을 호출한다. 목록에서 신규 종목을 헬스의 `0세트` 기록으로 표현하지 않는다. 상세의 실제 운동 시간과 공통 세션의 시작~종료 경과 시간은 구분한다.

목록은 인증 사용자 범위에서 필터링한 뒤 페이지를 나눈다. `cursor`는 기존 방식인 0 이상의 페이지 번호, `size`는 1~100으로 유지한다. 신규 목록은 `endedAt DESC, id DESC`로 정렬하고 기존 공통 목록의 정렬 계약은 유지한다. Android에서 한 페이지를 받은 뒤 종목 필터로 버리는 방식을 사용하지 않는다.

## 4. 저장 필드와 종목별 계약

| 필드 | 필수 | 규칙 |
|---|---|---|
| `clientRecordId` | 예 | 기기에서 한 번 생성한 UUID. 재시도 시 동일 값 |
| `sportCode` | 예 | `BADMINTON`, `CLIMBING`, `HIKING`, `GOLF` |
| `activityType` | 예 | 아래 종목별 유형 중 하나 |
| `startedAt`, `completedAt` | 예 | UTC ISO 8601 시각. 날짜는 별도 저장하지 않고 표시 시 계산 |
| `activeDurationSeconds` | 예 | 1 이상의 정수, 시작~종료 경과 초 이하. 휴식 제외 |
| `placeName` | 아니요 | 장소 자유 입력, 최대 100자 |
| `memo` | 아니요 | 최대 500자 |
| 종목별 결과 필드 | 아니요 | 모두 생략해도 시간 기록 저장 가능 |

| 종목 | `activityType` | 선택 결과 필드 |
|---|---|---|
| 배드민턴 | `SINGLES`, `DOUBLES`, `PRACTICE` | `gameCount`, `winCount` |
| 클라이밍 | `BOULDERING`, `LEAD`, `TOP_ROPE` | `attemptCount`, `completionCount`, `difficultyMemo` |
| 등산 | `HIKE`, `TREKKING` | `courseName`, `distanceMeters` |
| 골프 | `PRACTICE`, `SCREEN`, `FIELD` | 연습: `shotCount`. 스크린·필드: `holeCount`, `strokeCount` |

- 횟수 필드는 0~9999의 정수. `holeCount`는 입력 시 1~18로 부분 라운드도 허용한다.
- `winCount`가 있으면 `gameCount`가 필요하고, 승리 수는 게임 수 이하여야 한다.
- `completionCount`가 있으면 `attemptCount`가 필요하고, 완등 수는 시도 수 이하여야 한다.
- `strokeCount`가 있으면 `holeCount`가 필요하고, 총 타수는 1~9999다.
- 거리 입력은 0~1,000,000m의 정수. Android에서 km를 m로 변환한다. 미입력 null과 직접 입력한 0을 구분한다.
- `difficultyMemo`, `courseName`은 최대 100자. 문자열은 앞뒤 공백을 제거하고 선택 문자열의 빈 값은 null로 정규화한다.
- 다른 종목의 필드, 골프 연습에 홀·타수, 스크린·필드에 타격 수가 포함되면 400으로 거절한다. 유형 변경 시 프론트에서도 불필요한 값을 제거한다.

예시 요청은 가상 시연 데이터다.

```json
{
  "clientRecordId": "a64b0b9d-b462-4ff8-8d03-77c7e507c642",
  "sportCode": "BADMINTON",
  "activityType": "DOUBLES",
  "startedAt": "2026-09-14T05:00:00Z",
  "completedAt": "2026-09-14T05:02:00Z",
  "activeDurationSeconds": 90,
  "placeName": "시연 체육관",
  "gameCount": 3,
  "winCount": 2,
  "memo": "기능 시연용 예시 기록"
}
```

### 4.1 저장 성공·상세 응답

최초 POST는 201, 동일 내용 재시도와 상세 GET은 200이며 본문 구조는 같다. `id`는 요청의 `clientRecordId`와 동일하고 응답에는 `clientRecordId`를 중복해서 넣지 않는다. 업무 필드는 정규화된 값이며 선택 필드는 미입력 시 명시적인 null로 반환한다. 날짜와 시각은 UTC ISO 8601이고 소수 초는 최대 밀리초 정밀도다. 프론트는 시각 문자열 길이로 파싱하지 않는다.

```json
{
  "data": {
    "id": "a64b0b9d-b462-4ff8-8d03-77c7e507c642",
    "sportCode": "BADMINTON",
    "activityType": "DOUBLES",
    "startedAt": "2026-09-14T05:00:00Z",
    "completedAt": "2026-09-14T05:02:00Z",
    "activeDurationSeconds": 90,
    "elapsedDurationSeconds": 120,
    "placeName": "시연 체육관",
    "memo": "기능 시연용 예시 기록",
    "gameCount": 3,
    "winCount": 2,
    "attemptCount": null,
    "completionCount": null,
    "difficultyMemo": null,
    "courseName": null,
    "distanceMeters": null,
    "shotCount": null,
    "holeCount": null,
    "strokeCount": null
  }
}
```

`elapsedDurationSeconds`는 밀리초로 정규화한 시작~종료 간격의 정수 초다. `activeDurationSeconds`는 1~2,147,483,647의 정수이며 이 경과 초 이하여야 한다. 요청의 선택 필드 생략과 null은 같은 의미다. 명시적인 0은 null로 바꾸지 않는다. 적용되지 않는 종목 필드는 null 또는 생략만 허용한다.

### 4.2 목록 응답과 필터

신규 `/sport-records`의 각 `items` 원소는 4.1의 `data` 객체와 같은 구조다. 다음 페이지가 있으면 `nextCursor`는 다음 페이지 번호의 문자열이고 `hasNext=true`다. 마지막 페이지는 `nextCursor=null`, `hasNext=false`이며, 빈 목록은 아래와 같다.

```json
{
  "data": {
    "items": [],
    "nextCursor": null,
    "hasNext": false
  }
}
```

신규 목록에서 네 종목 밖의 `sportCode`는 400이다. 공통 `/workout-sessions` 필터는 기존 두 종목과 신규 네 종목을 허용하며 나머지는 400이다. 필터를 생략하면 각 API의 전체 범위를 반환한다. 빈 문자열·알 수 없는 코드·잘못된 cursor/size는 400으로 처리한다.

공통 목록은 기존 `WorkoutSessionSummaryResponse`를 유지한다. 신규 종목의 한 행은 다음 형태다.

```json
{
  "id": "a64b0b9d-b462-4ff8-8d03-77c7e507c642",
  "sportCode": "BADMINTON",
  "routineId": null,
  "routineName": null,
  "routineSplitDayNo": null,
  "routineSplitCount": null,
  "routineWorkoutDayNumber": null,
  "status": "COMPLETED",
  "startedAt": "2026-09-14T05:00:00Z",
  "endedAt": "2026-09-14T05:02:00Z",
  "exerciseCount": 0,
  "completedSetCount": 0,
  "version": 0
}
```

공통 목록에는 `activityType`·활동 시간·종목별 수치가 없다. 신규 카드에는 종목·날짜를 표시하고 상세 GET에서 유형·활동 시간·수치를 표시한다. 기존 필드인 0세트/운동 수를 신규 종목의 결과로 표시하지 않는다. 신규 상세의 `completedAt`과 공통 목록의 `endedAt`은 같은 시각이며 목록 정렬은 각각 3절의 계약을 따른다.

## 5. 저장과 실패 처리

1. 인증 사용자와 종목·유형·시간·수치 범위를 검증한다.
2. 같은 ID가 있으면 소유자와 신규 종목 기록 여부를 먼저 확인한다. 타인 소유 ID는 404, 본인의 다른 종류 기록 ID는 409로 처리한다.
3. 동일 ID·동일 정규화 내용이면 기존 기록을 반환한다. 내용이 다르면 409로 거절하여 저장 후 편집으로 동작하지 않게 한다.
4. 공통 세션과 상세 행을 하나의 트랜잭션에서 저장한다. 상세 실패 시 세션도 롤백한다.
5. 동시 동일 요청은 PK 충돌로 한 번만 생성한다. 충돌 트랜잭션을 종료한 뒤 별도 조회에서 소유자·내용을 다시 확인한다. 롤백된 트랜잭션에서 조회를 계속하지 않는다.
6. 시각은 DB 정밀도에 맞춰 밀리초로 정규화한 뒤 비교한다. 수치와 null/빈 문자열의 비교 기준은 저장 전 정규화와 동일하게 한다.

### 5.1 오류 계약

| HTTP | `error.code` | 의미 |
|---|---|---|
| 400 | `VALIDATION_ERROR` | 입력·필터 오류, 신규 기록에 헬스 리포트 요청 |
| 401 | 기존 인증 오류 코드 | 토큰 만료·누락·유효하지 않음. 기존 인증 처리 유지 |
| 404 | `RESOURCE_NOT_FOUND` | 기록 없음 또는 타인 소유 |
| 409 | `SPORT_RECORD_CONFLICT` | 같은 ID에 다른 본문 또는 본인의 다른 종류 기록 존재. 이 코드를 추가 |
| 409 | `INVALID_STATE_TRANSITION` | 완료 신규 기록에 기존 상태 변경·세트 쓰기 API 요청 |

기존 `ApiException`에 기본값이 빈 목록인 `fields: List<ApiErrorField>`를 추가하고 `GlobalExceptionHandler`가 해당 값을 전달하게 한다. 기존 호출자의 빈 fields 응답은 유지한다. 신규 서비스의 업무 검증은 요청 필드명을 넣고, reason은 `REQUIRED`, `OUT_OF_RANGE`, `INCONSISTENT_VALUE`, `NOT_ALLOWED` 중 해당 값을 사용한다. 필수 합계가 없으면 합계 필드에 `REQUIRED`, 합계 초과는 입력한 부분 수치 필드에 `INCONSISTENT_VALUE`를 지정한다.

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "승리 수는 게임 수를 넘을 수 없습니다.",
    "fields": [
      { "field": "winCount", "reason": "INCONSISTENT_VALUE" }
    ]
  }
}
```

Bean Validation의 기존 reason인 `Min`, `Max`, `Size` 등은 보존한다. JSON 파싱·알 수 없는 enum·인증 오류는 fields가 비어 있을 수 있다. 프론트는 알려진 필드의 오류를 해당 입력에 연결하고, 그 외에는 message를 화면 오류 영역에 표시한다. 메시지 문자열로 오류 종류를 분기하지 않는다.

ID 내용 충돌의 본문은 아래와 같다. 타인 소유 ID에는 이 응답이나 기존 내용을 노출하지 않고 404를 사용한다.

```json
{
  "error": {
    "code": "SPORT_RECORD_CONFLICT",
    "message": "같은 기록 ID에 다른 내용이 저장되어 있습니다.",
    "fields": []
  }
}
```

공통 세션 API의 운동 추가·세트 변경·상태 변경과 헬스 리포트 경로에 신규 네 종목이 잘못 들어오면 명시적으로 거절한다. 기존 헬스·러닝 경로의 동작은 보존한다. 신규 결과에 세트 필수 조건을 적용하거나 가짜 헬스 세트를 생성하지 않는다.

## 6. 구현 순서와 완료 기준

| 순서 | 구현 단위 | 완료 판단 |
|---|---|---|
| 1 | DB 계획과 DTO 필드 매핑 | 네 종목·유형·필드가 DB/Android와 일치 |
| 2 | 엔티티·repository·생성 서비스 | 세션과 상세 원자 저장, 동일 ID 재시도 처리 |
| 3 | 상세·목록과 공통 목록 필터 | 소유자 격리, 페이지 이전 서버 필터 |
| 4 | 기존 세트 API 진입 방어 | 신규 기록을 헬스 데이터로 변경할 수 없음 |
| 5 | Android 계약 전달 | 저장 예시와 오류·재조회 응답으로 연결 가능 |

이 표는 구현 순서이며 담당자 배정이나 완료 이력이 아니다. 후속 업무 상태는 결정 로그에 기록한다.

## 7. 해당 기능만 검증하는 계획

- 신규 네 종목의 시간만 저장, 종목별 결과 저장, 상세·목록 재조회.
- 잘못된 유형·필드 조합, 음수, 승리/완등 수 초과, 잘못된 시간 거절.
- 같은 ID 재전송·동시 요청·내용 충돌, 다른 사용자 조회, 상세 실패 시 롤백.
- 혼합 종목 데이터를 여러 페이지에 배치한 뒤 종목 필터 누락·중복 확인.
- 신규 세션의 헬스 쓰기 API 진입 거절, 기존 헬스·러닝 기록의 최소 조회 회귀 확인.
- `RoutineQueryApiIntegrationTest`의 종목 카탈로그 기대값을 실제 display_order인 `HEALTH`, `RUNNING`, `BADMINTON`, `HIKING`, `CLIMBING`, `GOLF` 및 해당 기존 UUID 여섯 개로 변경한다. 종목 코드뿐 아니라 ID 배열 단정도 함께 수정한다.
- 활성화의 직접 영향만 확인한다. 신규 종목으로 가입·프로필 저장/재조회, 기존 메이트 모집 생성/조회가 같은 종목을 유지하는지 확인하고 신규 메이트 운동 시작은 구현하지 않는다.
- 업무 검증 fields 전달과 기존 오류 응답 보존을 검사한다. 프론트의 저장 성공·실패 처리는 이 문서의 JSON 계약으로 별도 담당자가 구현한다.

후속 구현 때 신규 API와 직접 영향받는 목록·카탈로그·프로필/가입·메이트 종목 및 오류 응답 테스트만 클래스/메서드로 지정한다. 기존 기능 전체를 재검증하지 않는다. DB 이행 테스트 범위는 DB 계획 7절을 따른다. 테스트 DB가 없어 통합 검증을 못 했다면 통과로 표시하지 않고 미실행 이유를 인계한다.

## 8. 백엔드·DB 완료와 인계

- 네 종목의 시간만 저장·결과 저장·상세·목록·중복 재시도를 실제 API로 확인한다.
- DB 계획의 이행 및 직접 영향받는 기존 검사 결과를 기록한다.
- 프론트 담당자에게 이 문서의 경로·요청/응답·오류·null·ID 재시도·목록 분기 계약과 구현 revision, 실행한 검사 및 미실행 항목을 전달한다.
- 백엔드·DB 완료와 Android/시연 완료를 별도로 표시한다. 프론트 코드 수정과 실제 발표 준비를 이 담당의 완료 조건으로 추가하지 않는다.

이번 문서 개정에서는 테스트·빌드·서버·DB를 실행하지 않았으며 전체 테스트는 실행하지 않는다.
