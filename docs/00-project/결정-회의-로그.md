## 2026-09-05 Backend A P0 구현 결정

| 항목 | 결정 |
|---|---|
| Java | Backend는 Java 17로 고정한다. |
| 알림 설정 | P0에서 설정값 저장만 구현하고 `core_notification_settings`는 V3 migration으로 추가한다. Push 발송과 device token은 제외한다. |
| 시설 입력 | 빠른 P0 구현을 위해 기존 `activityRegionIds`, `facilityNames` 계약을 유지한다. 시설명이 있으면 활동 지역은 정확히 1개만 허용하고 해당 지역에 시설을 연결한다. |
| 회원가입 중복 요청 | 회원가입에서는 `Idempotency-Key`를 사용하지 않는다. 정규화 이메일 unique와 단일 트랜잭션으로 중복 계정을 방지한다. |
| Token | access JWT는 15분, refresh token은 30일로 한다. P0는 환경변수 secret을 사용하는 HS256과 opaque refresh token rotation을 적용한다. |
| 비밀번호 | 8~64자, 문자·숫자 각각 1개 이상, UTF-8 72바이트 이하로 검증하고 BCrypt hash만 저장한다. |
| 필수 약관 철회 | 개발·시연용 P0에서는 활성 계정의 필수 약관 철회를 허용하지 않는다. 선택 약관만 철회할 수 있다. |
| 회원 탈퇴 | P0에서는 `WITHDRAWN`, `withdrawn_at`, 프로필 `deleted_at`, 전체 세션 폐기와 `auth_version` 증가까지만 처리한다. 실제 삭제·익명화는 후속 정책으로 미룬다. |
| 약관 타입 | 별도 변환 없이 DB 값인 `SERVICE_TERMS`, `PRIVACY`를 API에서도 사용한다. |
| PR | 공통 기반, 인증·회원가입, 프로필·동의·탈퇴, 알림·통합 테스트의 4개 PR로 나눈다. |

## 2026-09-07 Android 연동 계약 변경

사용자가 `헬스 선택 정책·지역 계약부터 변경`으로 명시 승인했다.

| 항목 | 결정 및 반영 |
|---|---|
| 가입 관심 운동 | HEALTH 필수를 해제한다. 활성 운영 운동 또는 커스텀 운동 중 최소 1개는 필요하다. 러닝만 또는 커스텀 운동만 선택한 가입을 허용한다. |
| 프로필 수정 | 수정 후 운영 운동과 커스텀 운동이 모두 비지 않도록 검증한다. 누락된 필드는 기존 값을 유지한다. |
| 지역 | 시·도 → 시·군·구 → 읍·면·동 선택을 제공한다. 법정동을 사용하며 행정동·리 단위는 제외한다. |
| 데이터 이행 | 기존 지역 UUID와 V1~V5 migration을 보존하고 V6에서 공식 법정동 데이터를 추가한다. 폐지 시·도는 삭제 대신 비활성화한다. |
| 시설 | 기존 지역 UUID + 시설명 계약을 유지한다. 동 단위 지역으로 가입 후 시설 재조회까지 확인한다. |
| HEALTH 미선택 추천 | 자동 헬스 추천을 강요하지 않는다. 헬스 템플릿·사용자 루틴 선택은 별도로 제공한다. |

### 기존 Action Items

- Backend Gradle toolchain과 실행 문서를 Java 17로 변경한다.
- JDK 17 환경에서 빌드하고 MySQL 8.4 통합 테스트 환경을 준비한다.
- 기존 V1/V2는 수정하지 않고 알림 설정 V3 migration을 추가한다.
- 승인된 계약을 기준으로 Backend A API와 테스트를 구현한다.

| API 계약 | 메이트 응답은 작성자·신청자 요약, 정원/남은 자리, 시각, 방 상태·읽음 위치를 제공한다. 알림은 기존 Android 연동 계약인 `notificationId`, `resourceType`, `resourceId`를 유지한다. |

- SDK 유지, 발표 전용, 외부 요약 3일, 배포·백업·삭제·철회·탈퇴 신규 기능 제외 범위는 유지한다.

이번 작업은 문서 개정과 코드 검토이며, 기기 시연이나 DB 통합 테스트를 새로 실행한 기록은 아니다.

## 2026-09-09 Galaxy Fit3 계획 검토 의견 반영

이 절은 v0.3 검토 이력이다. 아래의 승인 대기·주기 삭제 제안과 관련 Action Item은 후속 ‘단일 테이블 승인과 발표 후 수동 정리’ 결정으로 대체됐다.

사용자가 중복 키·보관과 삭제 시점·수정 시각 획득 경로에 대한 검토 의견을 전달하고 단일 테이블 구조의 승인 여부를 먼저 결정하도록 요청했다.

- v0.3에서 원본 중복 키를 기존 DB 기획의 `(user_id, provider, source_app_id, source_record_id)`로 맞췄다. nullable 앱 출처는 generated key로 DB 중복 방지를 보완한다.
- 공식 API와 로컬 SDK 1.1.0 AAR의 getter를 확인해 `sourceModifiedAt`은 `readData()`의 `HealthDataPoint.updateTime`에서 얻도록 명시했다. `readChanges()` 신규 도입은 필요하지 않다.
- 단일 테이블 단순화와 ‘72시간 조회 만료·정상 실행 중 60초 주기 행 삭제·재시작 정리’는 검토 가능한 추천안으로 기록했다. 기존 두 테이블과의 차이 및 서버 중단 시 삭제 지연을 명시했다.
- 위 구조·파기 세부안은 아직 승인되지 않았다. 승인 후 DEMO-03~04의 구현 지시서로 사용한다. SDK 유지·발표 전용·약 3일 사용·백업과 사용자용 삭제/철회/탈퇴 기능 제외 범위는 유지한다.

### 후속 Action Items

- 단일 테이블 단순화와 조회 만료·물리적 삭제 세부안의 사용자 판단을 기록한다.
- 승인된 구조에 맞춰 migration의 출처 앱 포함 unique, null 앱 중복 방지, 주기 삭제·장애 후 재시도와 수정 시각 매핑을 검증한다.

| 발표 후 정리 | 개발 담당자가 발표용 테스트 데이터를 개발 DB에서 수동으로 정리한다. 자동 정리 기능이나 사용자용 삭제 API는 만들지 않는다. |

| 이번 작업 | 계획서 v0.4와 이 로그만 수정한다. 코드·설정·migration 구현 및 실제 DB 정리는 실행하지 않는다. |

세부 구현 범위는 [발표용 연동 계획 v0.4](../02-technical/galaxy-fit3-발표용-연동-구현-계획.md)에 반영한다. 단일 테이블이나 삭제 주기에 대한 추가 승인 대기는 없다.

### 후속 Action Items

- 후속 구현 요청 시 v0.4의 DEMO-01~04를 기준으로 최소 요약 저장·재조회 시연을 완성한다.

## 2026-09-09 Galaxy Fit3 현재 브랜치 검토와 시연 추천 반영

사용자는 현재 브랜치의 migration·이행 검증 기준을 최신화하고, 구현·시연이 쉬운 추천 방향을 계획에 반영하도록 요청했다. WBS 관련 부분은 사용자가 직접 관리하므로 수정하지 않도록 지정했다.

- `main` 브랜치 `fedb4c0`의 migration V1~V19와 `MateMigrationUpgradeIntegrationTest`의 V13 이후 6개 이행 단정을 정적으로 확인했다. 외부 요약은 현재 기준 V20으로 계획하며 기존 V19 메이트 상세 확장을 보존한다.
- [발표용 연동 계획](../02-technical/galaxy-fit3-발표용-연동-구현-계획.md)을 v0.5로 갱신했다. 메이트 이행은 V19까지 유지하고 외부 요약의 V19→V20 및 빈 DB 이행을 별도로 검증하도록 기술 기준을 보완했다.
- 구현 추천은 서버 헬스 세션 하나와 실제 Fit3 단일 운동 기록 하나를 연결하는 방식이다. 실제 조회로 확인한 근력 운동 코드 하나를 허용하고 전체 세션 요약으로 표시한다. 해당 코드값은 이번 정적 검토에서 확정하지 않았다.
- 발표 추천은 별도로 준비한 미연결 기록 한 쌍을 사전 동기화한 뒤 현장에서 후보 확인·저장·재조회를 보여주는 방식이다. 최초 버전, 동일 PUT 재시도, 동일 원본 갱신 및 응답 유실 복구 계약도 계획에 구체화했다.
- WBS 파일과 계획서 10절의 작업 표·일정·설명은 수정하지 않았다. 해당 표의 기존 V19 표기와 최신 기술 기준의 차이는 계획서 도입부에 안내했다.
- 승인된 단일 테이블·최소 저장·발표 후 수동 정리 범위는 유지한다. 이번 작업은 문서 개정이며 코드·migration·테스트 파일 수정, 테스트·빌드·앱·서버·DB 실행은 하지 않았다.

## 2026-09-09 Galaxy Fit3 응답 유실 복구 비교 보완

사용자가 서버 반올림 전후 값의 차이로 Android가 저장 성공을 오판할 수 있다는 P2 검토 의견을 전달했다. 계획서 v0.6에 Android도 서버와 같은 정규화를 적용하고 요청의 요약·원본 필드만 비교하도록 반영했다. 세션 ID는 대상 확인에 사용하고 버전·저장 시각 등 서버 관리 필드는 내용 비교에서 제외한다. 반올림된 GET 값으로 저장 완료를 복원하는 경우와 실제 값이 다른 경우의 후속 검증 계획을 추가했다. WBS·코드·테스트 파일은 수정하지 않았으며 테스트·빌드·앱·서버·DB는 실행하지 않았다.
